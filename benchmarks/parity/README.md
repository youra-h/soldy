# Одинаковость платформ

Один и тот же сценарий пользователя на шести платформах — Vue, React, Svelte, Solid, Web
Components, Angular — и после каждого шага запись: события компонента (имя, данные, порядок),
дерево доступности (роли, имена, состояния, значения) и узел в фокусе. Записи пяти платформ
сверяются с Vue; расхождение, которого не объясняет правило сравнения, — дефект адаптера. Здесь —
стенд, методика и правила. Итоги и что из них можно утверждать — [`report.md`](report.md).

Это не замер производительности, а сверка, но её стенд — стенд страниц
([`pages/`](../pages/README.md)), и журнал лежит рядом с ними. Журнала на платформу нет: каждая
запись — сравнение платформы с эталоном, и итог одного прогона — один отчёт.

## Стенд

[`tools/bench-pages/`](../../tools/bench-pages/) — та же страница, что у замера страниц
(`index.html?fw=<фреймворк>`): хосты превью стенда разработчика, одни данные и одни сценарии
(`scenarios.ts`) на все платформы. Для сверки страница монтирует компонент одной копией и
слушает его события (`bench.record`): хост отдаёт все объявленные события компонента и фасада
коллекции под полными именами ядра (`onEvent` в `TPreviewMount`).

Слушаются и части, которые превью ставит разметкой (`parts` записи реестра стенда): табы и
панели Tabs, элементы ListBox, секции Accordion, радио RadioGroup и все пять видов пунктов Menu
(`Item`, `CheckboxItem`, `RadioItem`, `Submenu`, `PopoverItem`). Событие части приходит под её
именем в экспорте: `Tabs.Item>action:press` (`partsOf` в `packages/playground/shared`).
Слушатели — по поверхности дескрипторов части, как у самого компонента; у Angular их ставит
директива `pg-part` на элементе части — до сборки, как привязки выходов в шаблоне, — у Web
Components — описание части в превью (`TPreview.part`), на её элемент. Части, которые владелец
рисует сам из `items`, — теги Tags, страницы Pagination, опции Select на странице сверки, —
потребителю недоступны, и их не слушают.

DatePicker на странице сверки — с подвалом (`confirmable`, `recordedPropsOf` в `bench.ts`), а
пропсы страницы замера прежние: подвал поменял бы то, что мерят её журналы.

```bash
npm run test:parity                                       # сборка, все платформы, отчёт
cd tools/bench-pages
node parity.mjs --fw vue,react --pages select,menu        # записи results/parity-<платформа>.json
node parity-report.mjs --fw react                         # отчёт results/parity-report.md
```

Флаги `parity.mjs`: `--fw` — платформы через запятую, `--pages` — страницы (без него — все
страницы компонентов), `--no-build` — без сборки страницы. Сборка — без минификации, в
`dist-prof`, как у снимка кучи: в записи — настоящие имена классов. Отчёт сверяет каждую
платформу с `results/parity-vue.json`; код выхода — число платформ с расхождениями (и Vue, если на
его страницах были ошибки консоли).

## Методика

Платформа — свой браузер, одна страница, окно 1600×1000. Для каждой страницы компонента:

1. **Монтирование** одной копии; события идут в журнал с аргументами в сравнимом виде (`comparable`
   в `bench.ts`), снятыми в момент события: примитивы как есть, экземпляр ядра — класс и `value`,
   событие действия — класс, поля и `defaultPrevented`, событие и узел DOM — тип и тег,
   множество и словарь — содержимым, прочий объект (плагин, движок) — только классом.
2. **Сценарий** страницы — те же действия, что у замера страниц: нажатия полной цепочкой указателя,
   набор (`insertText`), клавиши, открытие и закрытие оверлеев, прокрутка. После каждого действия
   сценарий зовёт наблюдателя шага (`observeSteps` в `scenarios.ts`), страница ждёт покоя — ни
   одной идущей конечной анимации или перехода и три кадра без изменений DOM, не дольше 3 с, —
   и прогонщик пишет шаг: события с прошлого шага, снимок доступности всего документа
   (`ariaSnapshot()` Playwright — с панелями, которые слой уносит в конец `body`) и узел в фокусе
   — самый глубокий, сквозь теневые корни: тег и строка его снимка. У DatePicker с подвалом
   сценарий ещё жмёт его кнопки: открыть, выбрать день, «Отмена»; открыть, выбрать день,
   «Готово». На странице замера подвала нет, и её шаги прежние. Сами кнопки — детали разметки
   DatePicker, а не части: потребитель их не слушает, и порядок их действия относительно
   событий DatePicker сверка не видит — шаги проверяют, что вышло.
3. **Снятие** — последний шаг, только с событиями: после начала снятия их нет (см. правила).

Метка шага — действие и узел: класс части (`so-select__arrow`), иначе блока, иначе тег; не первый
класс узла: их порядок — дело адаптера.

## Правила сравнения

Ожидаемое расхождение — правило с причиной (`RULES` в `parity-report.mjs`), а не исключение:

- **`update:<prop>`** — события `v-model` Vue; у остальных адаптеров `v-model` нет.
- **Идентификаторы и ключи** сравниваются наличием: `id` и ссылки на него (`aria-controls`,
  `aria-labelledby`, `for`, `data-owner`…) строятся от id монтирования, а ключи секций и
  нарисованных строк (`key`) — от счётчика страницы. Что они связывают — имена и описания, —
  сверяет дерево доступности.
- **Одно значение у события** Angular (`emit`) и Web Components (`detail`): событие с несколькими
  аргументами приходит их кортежем, без аргументов — `undefined` (`null` в `detail`, как его
  заполняет платформа). Корень Icon в Web Components — `span` с рисунком внутри: элемент расширяет
  только тег HTML, `svg` — нет.
- **Снятие сравнивается событиями**: после начала снятия потребитель не слышит ничего. Его
  первый миг — фаза `detach` контекста, и на ней адаптер отписывает потребителя: Vue — в
  `onBeforeUnmount`, React — очисткой layout-эффекта, Svelte — очисткой пред-эффекта
  (`$effect.pre`), созданного раньше блоков шаблона, Solid — очисткой вычисления, которое адаптер
  заводит под тем же владельцем после монтирования, последним (`detachFirst` в `useAdapter.ts`
  адаптера). Снятый элемент Web Components и снятый компонент Angular событий не шлют: Angular
  снимает поддерево с конца, но сначала выносит его из документа. `detach` владельца коллекции
  отсоединяет и её участников — элементы и панели Tabs (`TCollectionMembers`): Svelte, Solid и
  Angular снимают их по одному, и элемент, которого ещё слышат, слышал, как уходят соседи
  (`change:order`, переезд активности). Без этого потребитель слышал, как уходят дети: выход
  элементов разметки из коллекции списком всё короче — запись его в своё состояние опустошала
  список вместе с владельцем, — и отвязку корня. Правило `removedBlur` — потеря фокуса снятым
  узлом у Svelte, Web Components и Angular: они убирают узлы раньше любого хука компонента, а
  Chrome снимает фокус с узла до того, как тот отсоединён, и потребитель слышит `action:blur` и
  `change:focused` компонента в фокусе.
- **События узла** — `ready`, `element:ready`, `element:removed` компонента и частей —
  сравниваются содержимым, а не местом (`nodeOrder`) у React, Svelte, Solid и Web Components.
  Они приходят в том порядке, в каком фреймворк привязывает и отвязывает узлы: Vue, React и
  Angular — детей раньше родителя, Svelte, Solid и Web Components — родителя раньше, Solid
  вынимает узел панели на той же записи, что её прячет, а Vue — своей отрисовкой после клика.
  Остальные события шага — по порядку.
- **`change:order` частей при монтировании у React** (`enteredBefore`) не сравнивается. React
  рисует все элементы списка раньше, чем принимает хоть один, и фасад элемента следит за
  коллекцией с отрисовки: элемент, ещё не вошедший, слышит `change:order`, пока входят соседи
  до него. Vue создаёт и принимает элементы по одному, и элемент слышит только тех, кто после.
  Свой вход элемент не слышит ни у кого: что пишет приём, — начальное состояние (у React —
  `TBuilt.accept`).

## Сторож

`npm run test:parity` в задаче CI «Тесты — браузер (chromium)», после браузерного прогона в
Chromium: все страницы на всех платформах, отчёт с расхождениями роняет задачу. Прогон идёт около
двух минут. Сравнение сначала
проверяет себя (`selfCheck`), как замер страниц — подставной утечкой: шаг Vue с переставленными
событиями и лишней строкой дерева обязан найтись дважды — порядком и деревом, иначе отчёт падает.
