# Проверка утечек памяти и веса страниц: как проводилась

Отчёт о проверке, которую soldy прошёл на всех шести платформах 25–26 октября 2026 года
(задача [869fhddjf](https://app.clickup.com/t/869fhddjf)). Здесь всё, что нужно для статьи о
ней: что проверяли и зачем, как устроен стенд, как проверяли сам замер, итоги с цифрами, что из
них можно утверждать и чего нельзя, как повторить. Полные таблицы платформ — журналы
`<платформа>.md` рядом, методика кратко —
[`README.md`](README.md).

## Коротко

- **Утечек нет ни на одной из шести платформ** — Vue, React, Svelte, Solid, Web Components,
  Angular. Каждый из 34 компонентов прошёл 22 цикла «смонтировать 50 копий → поработать с ними →
  сменить язык → снять страницу», и после снятия не осталось ни одного лишнего экземпляра
  компонента, шины событий, узла DOM или слушателя событий, а куча от цикла к циклу не росла.
- **Смена страниц ничего не копит**: три круга по всем 34 страницам подряд без перезагрузки — и
  после каждого круга куча, узлы, слушатели и экземпляры те же, до единицы.
- **Сам замер проверен**: подставная утечка — кнопка, которая после снятия держит свой узел,
  слушатель и экземпляр ядра, — видна на каждой платформе: ровно +50 экземпляров и +50
  слушателей за цикл из 50 копий.
- **Объём**: на каждой платформе — около 46 тысяч монтирований и снятий компонентов и около
  15,8 тысячи действий пользователя (клики, ввод, открытие и закрытие оверлеев, прокрутка); на
  шести — около 276 тысяч монтирований и 94 тысяч действий. 814 замерных циклов на платформу,
  после каждого шага — сборка мусора и замер.

## Что проверяли и зачем

Утечка памяти в библиотеке компонентов — то, что остаётся в памяти после того, как компонент
убрали со страницы: подписка на `document`, которую забыли снять, таймер, замыкание, которое
держит узел. В одностраничном приложении страницы сменяются без перезагрузки, и утечка копится:
каждый переход оставляет ещё немного, и через час работы вкладка весит гигабайт. Руками её не
проверить — она не видна ни глазами, ни юнит-тестом, только по памяти между многими циклами.

Вопросы проверки:

1. Уходит ли из памяти всё, что принёс компонент, когда страницу с ним снимают, — у каждого
   компонента, на каждой платформе?
2. Не копится ли что-то от смены компонентов — в общих реестрах, слоях оверлеев, кэшах?
3. Сколько весит страница из десятков одинаковых компонентов и сколько её монтировать?

## Стенд

- **Страница компонента** — 50 копий компонента рядом, одним корнем фреймворка, под одним
  провайдером языка: как десятки одинаковых полей или кнопок на странице приложения.
- **Компоненты на всех платформах одни.** Их рисуют превью стенда разработчика soldy: у каждого
  из шести адаптеров своё превью каждого компонента с одними и теми же типовыми данными —
  подписью кнопки, пятью элементами списка, строками таблицы, пунктами меню с подменю. Поэтому
  платформы сравнимы между собой: на каждой стоит одна и та же разметка.
- **34 компонента**: Button, Input, NumberInput, Textarea, CheckBox, Switch, Label, Field, Slider,
  Rating, RadioGroup, Select, Calendar, DateInput, DatePicker, Popover, Menu, Tooltip, Dialog,
  Drawer, Toasts, Scroller, ListBox, Pagination, Table, Tabs, Tags, Accordion, Icon,
  ProgressLinear, ProgressSpinner, Skeleton, DragAndDrop (три коллекции с перетаскиванием) и
  Virtual (окно над ListBox, Select и Table по 1000 элементов).
- **Служебные страницы**: `all` — все 34 компонента сразу, каждый своим корнем; `empty` — корень
  без компонентов, шум самого замера; `leak` — подставная утечка.
- **Окружение**: продакшн-сборка (Vite 8.3.4); Chromium 156.0.8078.4 через Playwright 1.64.1,
  окно 1600×1000; Vue 3.5.44, React 19.3.1, Svelte 5.57.2, Solid 1.9.17, Angular 22.2.3 без
  Zone.js, Web Components — без фреймворка; soldy 0.3.0-alpha.5 исходниками. Машина — AMD Ryzen 9
  9950X3D (16 ядер, 32 потока), 62 ГБ, Windows 11, Node 24.20.0. Платформы шли параллельно,
  каждая своим браузером.

## Как шёл прогон

Платформа — свой браузер и одна страница без перезагрузки на весь прогон.

1. **Прогрев**: каждая страница по разу, без замера.
2. **Страницы по одной**: 2 цикла разогрева и 20 замерных. Цикл: смонтировать 50 копий → замер;
   сценарий пользователя на первых 10 копиях; язык поддерева туда и обратно (русский →
   английский); снять страницу → замер.
3. **Обход**: все 34 страницы подряд, три круга, замер после каждой.
4. **Подставная утечка** — последней, циклами, как страница.

**Сценарий** — то, что делает пользователь, у каждого компонента своё: нажать кнопку, отметить
флажок, набрать текст в поле, поставить значение ползунку и звезду оценке. У Select — открыть
список, выбрать, открыть снова и закрыть Escape, набрать текст и оставить список открытым до
снятия страницы; у DatePicker — открыть календарь и выбрать день; у Menu — открыть, отметить
пункт с флажком, выбрать действие; у Dialog и Drawer — открыть, набрать в поле внутри, закрыть
Escape; у Tooltip — навести с задержкой открытия и сфокусировать; у Toasts — показать три тоста,
включая «загрузка → готово», и снять страницу с живыми тостами; у Table — дважды отсортировать и
нажать строку; у Virtual — прокрутить до конца и обратно. События идут полной цепочкой указателя
(`pointerdown` … `click`), набор — так, как текст вставляет браузер. Сценарии одни на все
платформы и на каждой делают одно и то же число действий — это проверено отдельно.

## Как мерили

Перед каждым замером — две полные сборки мусора протоколом DevTools. Затем пять счётчиков:

| Счётчик                | Что это                                                       | Откуда                                       |
| ---------------------- | ------------------------------------------------------------- | -------------------------------------------- |
| куча                   | занятая память JavaScript                                     | `Performance.getMetrics`, `JSHeapUsedSize`   |
| узлы DOM               | все живые узлы, и отсоединённые тоже — их кто-то держит       | `Performance.getMetrics`, `Nodes`            |
| слушатели              | все живые слушатели событий, и на отсоединённых узлах         | `Performance.getMetrics`, `JSEventListeners` |
| экземпляры компонентов | живые объекты компонентов ядра soldy и их наследников         | `Runtime.queryObjects` по прототипу          |
| шины событий           | живые шины событий ядра — свои у каждого компонента и плагина | `Runtime.queryObjects` по прототипу          |

Узлы, слушатели и экземпляры — не оценка памяти, а число объектов. Если снятая страница что-то
держит, это число после снятия больше, чем до, и растёт с каждым циклом.

**Итог страницы**: **утечка** — после снятия экземпляров, шин, узлов или слушателей больше, чем
было, и рост копится (не меньше чем на половину числа циклов); **куча растёт** — счётчики на
месте, а наклон кучи за цикл втрое выше шума и не меньше 4 КБ; иначе **чисто**. Рост считается от
конца разогрева: первые циклы законно растят кучу — ленивые определения компонентов, кэши
форматов языка.

## Как проверяли сам замер

Замер, который ничего не нашёл, ничего не доказывает, пока не показано, что он умеет находить.

- **Подставная утечка.** Страница `leak` — 50 кнопок, и каждая после снятия держит свой узел,
  слушатель на `document` и экземпляр ядра, как компонент, который забыл отписаться. Замер видит
  её на каждой платформе: за цикл +50 экземпляров, +250 шин, +50 слушателей и столько узлов,
  сколько их у 50 кнопок на этой платформе (+150…+600). Прогон, который её бы не показал, был бы
  недействителен.
- **Шум.** Страница `empty` — корень без компонентов: наклон кучи 0–0,1 КБ за цикл на всех
  платформах. Порог «куча растёт» — 4 КБ за цикл.
- **Три ловушки, найденные по ходу и устранённые в методике**:
  - _Таймер приложения — не утечка._ У Toasts сразу после снятия оставалось 30–39 экземпляров и
    около 200 шин, а через 2,5 с — ноль. Держал таймер самого превью: кнопка «загрузка → готово»
    через 2 с меняет тот же тост. Таймеры самих тостов снятие останавливает — иначе тост жил бы
    свои 5 с. Поэтому счётчики сверяются «осевшими», после паузы 6 с, а то, что держалось только до
    паузы, журнал отмечает отдельно.
  - _Разогрев движка на первой странице._ У первой страницы прогона куча росла на 4,4 КБ за цикл:
    одна ступенька компиляции общего кода, после неё ровно; та же страница второй — 0,3 КБ.
    Отсюда прогрев всех страниц перед замером.
  - _Колебание ±1._ У Svelte число узлов после снятия ходит на ±1 от цикла к циклу (708–710) и не
    копится. Утечка даже в один узел прибавлялась бы каждым циклом, поэтому итог «утечка»
    требует роста, который копится.
- **Прототипы классов.** `queryObjects` считает и прототипы подклассов: 103 «компонента» без
  единой шины на пустой странице — это они, на всех платформах поровну.

## Что можно утверждать в статье

- На всех шести платформах ни один из 34 компонентов soldy не оставляет после снятия страницы
  ничего в памяти: ни экземпляров, ни узлов DOM, ни слушателей событий. Проверено 22 циклами по 50
  копий на компонент — с действиями пользователя, сменой языка и снятием страницы с открытыми
  оверлеями и живыми тостами.
- Смена страниц без перезагрузки ничего не копит: три круга по всем 34 страницам, и память и
  число объектов после каждого круга те же.
- Проверка проверена: подставная утечка видна на каждой платформе.
- Одна и та же страница на шести платформах весит и монтируется сопоставимо; легче всех — Web
  Components и React, тяжелее — Svelte и Angular (таблицы выше).
- Под окном Virtual в DOM живёт только видимое: у 50 копий окна над 3000 элементами — около 930
  узлов на копию, а не десятки тысяч.

## Чего утверждать нельзя

- **Сравнения с другими библиотеками** — в этой проверке его нет, мерился только soldy.
  Сравнение с библиотеками соседей есть только у таблицы (`../table/<платформа>.md`).
- **«Лёгкий компонент» по весу превью**: вес — превью целиком, с содержимым и обёртками (подпись
  Label у флажка, пункты меню, дни месяца), а не голый компонент.
- **Абсолютного времени**: платформы шли параллельно на одной машине, а события — из скрипта
  страницы (полной цепочкой, но не ввод операционной системы). Время годится для сравнения
  страниц между собой.
- **Других браузеров**: только Chromium.
- **«Под окном Virtual память только на видимое»**: строки и узлы — да, но экземпляр ядра есть у
  каждого элемента данных (около 3100 на копию, около 2 КБ и 5 шин событий на элемент): это
  модель коллекции, выбор и поиск идут по всем элементам.

## Как повторить

```bash
npm install                                           # в корне монорепо
npm run build:css --workspace=@soldy-ui/theme-oren
cd tools/bench-pages
npm run bench                                         # все платформы по очереди; одна — --fw vue
node report.mjs vue                                   # таблицы журнала из results/vue.json
```

Код стенда — `tools/bench-pages/`: `bench.ts` — страница, `scenarios.ts` — сценарии
пользователя, `run.mjs` — прогонщик и замер протоколом DevTools, `report.mjs` — таблицы и итог
страницы. Сырые итоги — `tools/bench-pages/results/<платформа>.json`, в git не идут. Одна
платформа идёт около 40 минут.
