### soldy ломается на 5000 строках

Таблица soldy на Web Components на 5000 строках не собирается: страница бросает `RangeError:
Maximum call stack size exceeded`, в DOM — 45 тыс. узлов вместо 125 тыс., «выделить все» не
отмечает ни одной строки, сортировка не меняет порядок. На 500 строках таблица работает. Цифр
у soldy поэтому нет.

Стек — рекурсия ожидания подключения (`packages/ui/webc/src/adapter/runtime/waiting.ts`):
закончив подключение, `connecting()` на нулевой глубине разбирает очередь ожидающих элементов,
каждый ожидающий в `_resume` → `connectedCallback` снова зовёт `connecting()`, и тот, закончив,
начинает разбор очереди заново, внутри первого. Глубина стека — число ожидающих элементов, то
есть растёт со строками.

```
RangeError: Maximum call stack size exceeded
    at Array.shift (<anonymous>)
    at drain (waiting.ts)
    at runAll (waiting.ts)
    at connecting (waiting.ts)
    at TElementBase.connectedCallback (element.base.ts)
    at _resume (element.base.ts)
    at runAll (waiting.ts)
    at connecting (waiting.ts)
    …
```

## 2026-10-25 — Web Components, после исправления очереди ожидания

[869fmcaub](https://app.clickup.com/t/869fmcaub). soldy — `main` на `fa7adbe18` с исправлением
очереди, в условиях сравнения: `webc:soldy+fit=none+width=3248+track`. 5000 строк × 20 колонок, 3
прогона, медиана; время — в секундах до успокоения кадров. Соседи и голый DOM не перемерялись —
их цифры из первого замера, того же дня и на той же машине.

```bash
npm run bench -- 5000 3 webc:soldy+fit=none+width=3248+track
```

### Исправление

Разбор очереди ожидания (`packages/ui/webc/src/adapter/runtime/waiting.ts`) теперь один на всё
подключение: подключение элемента из очереди, закончив, очередь не разбирает — пришедшее во время
него встаёт в конец той же очереди, и его забирает идущий цикл. Порядок прихода прежний, глубина
стека от числа ожидающих больше не зависит. Сторож — `packages/ui/webc/__tests__/waiting.spec.ts`:
50 тыс. ожидающих без переполнения и в порядке прихода.

### Память после снятия — не утечка

4,7 МБ на 5000 строк против 2,6 МБ на 1000: остаток растёт со строками. Снимок кучи после
размонтирования (`npm run heap -- 2000 unmount webc:soldy+fit=none+width=3248+track 1`) живых
строк не находит: классов soldy — единицы на всю страницу (кэши модулей: `TRouting`, `TSurface`,
`TPropSpec`, `TPlaceContext`), записей строк — ни одной. Из 1,47 КБ на строку 0,66 КБ — пустые
таблицы `WeakMap`: записи собраны, а ёмкость, выросшая под все строки, осталась; почти всё
остальное — скомпилированный код, который на строки не делится.

### Вывод

- Таблица soldy на Web Components на 5000 строках работает и среди библиотек быстрее всех по
  каждому действию, кроме размонтирования: рендер 1,73 с против 2,17 с у Spectrum, выделение —
  вдвое быстрее Carbon. DOM-узлов — вдвое меньше, чем у соседей.
- По памяти soldy тяжелее: 216 МБ против 70–79 МБ у Carbon и Spectrum — на уровне soldy на
  React (210 МБ) и легче, чем на Vue (296 МБ).
- «Сортировка ↑» дольше «↓» (1,32 против 1,03) — так же у soldy на React, Angular и Solid, то есть
  не от адаптера Web Components.
