# Серверный рендер на Solid

Страница со всеми компонентами soldy, тысячи раз подряд отрисованная на сервере адаптером Solid: всё ли уходит из памяти после каждого рендера и не смешиваются ли языки соседних запросов. Стенд и методика — [`README.md`](README.md).

## 2026-10-27 — первый замер

[869fmdbeg](https://app.clickup.com/t/869fmdbeg). soldy — ветка `task/869fmdbeg-ssr-memory` на `112b87b94`; 34 компонента, рендер — `renderToString` из `solid-js/web` (Solid 1.9.17).

```bash
npm run bench -- --dump
node report.mjs solid
```

Node 24.20.0, `all` и `empty` — 3000 рендеров, из них 600 разогрева; `leak` — 600, из них 150; замер через 150 рендеров; пауза перед осевшим замером — 3 с. Пять платформ шли параллельно, своим процессом каждая.

**Итог: утечек нет.** Живых экземпляров ядра после 3000 рендеров ровно столько же, сколько до первого, — ни один рендер не оставил за собой компонента или шины событий; наклон кучи — ниже порога; ни одна из 3000 разметок не разошлась с первой разметкой своего языка, а первые — каждая на своём языке. Подставная утечка видна: +1 компонент и +1 шина на рендер.

**Корень `renderToString` Solid снимает следующей задачей** — `setTimeout(dispose)` в самом `renderToString`. До неё всё, что рендер собрал, живо: на замере сразу после круга из трёх рендеров — 10 645 «компонентов» и 9462 шины против 103 и 0 до рендеров, после оборота таймеров — снова 103 и 0. Первая версия прогона не возвращалась в цикл событий между кругами (синхронный рендерер решал круг в микрозадачах), таймеры не срабатывали, и процесс вырос до 4 ГБ и упал на нехватке памяти примерно за 230 с. Сервер между запросами в цикл событий возвращается, и прогон теперь тоже (`setImmediate` между кругами, `setTimeout(0)` перед замером, [`README.md`](README.md), «Сценарий»). Для приложения вывод один: память Solid на сервере — страницы, отрисованные с прошлого оборота цикла событий, а не только текущая; у soldy своего в этом нет.
