# Замеры таблицы

Как таблица soldy держит большой объём рядом с таблицами других библиотек. Файл —
журнал: новый замер дописывается новым разделом, старые не переписываются, чтобы
было видно, что дала каждая правка.

## Стенд

[`tools/bench-table/`](../tools/bench-table/) — Vite-страница и прогонщик на Playwright.
Вне workspaces: зависимости других библиотек ставятся только в стенд и в монорепо не
попадают.

```bash
cd tools/bench-table
npm install                    # один раз: таблицы других библиотек
npm run bench -- 5000 3        # строк, прогонов, [библиотеки через запятую]
npm run bench -- 5000 3 soldy  # только наша таблица
npm run bench -- 5000 3 soldy+mode=none+cols=5  # флаги через «+»: без выбора, 5 колонок
npm run bench -- 5000 3 react:soldy,react:antd   # участники на React — с префиксом «react:»
npm run prof                   # профиль CPU soldy без минификации (5000 строк)
npm run heap -- 500 multiple   # снимок кучи soldy: что весит в строке; режим — multiple | none
npm run heap -- 5000 unmount react:soldy+track 1  # что пережило размонтирование: участник, замен[, пауза, мс]
npm run heap -- 500 mounted react:soldy+track 2   # что держит смонтированная таблица после замен: то же, без размонтирования
npm run trace -- 5000 soldy+reorder 3  # трасса жеста перестановки: строк, [библиотеки], [прогонов], [набор]
npm run trace -- 5000 soldy 3 rest     # трасса таблицы на покое: выбор и сортировки
npm run trace -- 5000 soldy+resize 3 resize  # трасса протяжки ручки ширины
```

`trace.mjs` рисует N строк и прогоняет набор сценариев — каждый под своей трассой Chromium
(`browser.startTracing`). Набор — последний аргумент: `reorder` (по умолчанию) — «Взять колонку»,
«Смена места» и «Отпустить», ему нужен флаг `reorder`; `resize` — «Взять ручку», «Шаг ручки» (указатель
на 20 px) и «Отпустить ручку» там же, ему нужен флаг `resize`; `rest` — таблица на покое: «Выделить
все», «Снять выделение», «Сортировка ↑» и «Сортировка ↓». По сценарию он печатает медиану: скрипт
главного потока — обработчики событий, вызовы функций из браузера, микрозадачи, — суммы фаз —
пересчёт стилей (`UpdateLayoutTree`), раскладку (`Layout`), обход перед отрисовкой (`PrePaint`),
отрисовку (`Paint`) и перестройку слоёв (`Layerize`), — отдельно пересчёт стилей внутри обработчиков
указателя (синхронный, вызванный чтением после записи) и наибольшее число элементов, чей стиль
пересчитан за раз. Скрипт — без двойного счёта: вложенные события скрипта (обработчик, функция в
нём, микрозадачи) — одно время, а фазы кадра, вызванные из скрипта, — в своих столбцах, а не в нём.
Флаги — те же, что у `run.mjs`.

`heap.mjs` снимает кучу дважды на одной странице, с пустой таблицей и с N строками, и
делит разницу на N. Разницу он раскладывает тремя способами: по конструкторам, по
первому владельцу внутренних узлов (массивы, контексты замыканий) и по ближайшему
«хозяину» в дереве доминаторов — классу soldy, экземпляру или VNode Vue, `Dep`. У
замыканий указана строка несжатой сборки (`dist-prof`). Узел, который держат двое,
относится к хозяину первого держателя, поэтому раскладка по хозяевам приблизительна.

В режиме `unmount` участник — запись `run.mjs` (флаги, `react:`), первый снимок — пустая
страница до рендера, второй — после сценария `run.mjs` до размонтирования включительно:
замен данных перед ним — сколько задано (первая — с тем же зерном, что у `run.mjs`), после
него — пауза, если задана. Сверх разницы по группам он печатает пережившие размонтирование
классы soldy и записи строк (штук на строку) и на каждый — кратчайшую цепочку удерживающих
от корня снимка по сильным рёбрам, с именами рёбер. Снимок сам собирает мусор до конца, и
что в нём осталось, держит корень.

Режим `mounted` — тот же сценарий без размонтирования: что держит смонтированная таблица после замен
(пауза, если задана, — после последней замены). Сверх разницы по группам он печатает живые записи строк,
штук на строку, разложенные по наборам, и на каждый набор — кратчайшую цепочку до его первой записи.
Набор — хвост цепочки удерживающих (последние четыре звена, номера элементов стёрты) и массив в нём:
записи одного списка лежат в одном массиве, у каждого держателя свой, а записи, которые держат поштучно
(снимок состояния строки), делятся по виду цепочки.

- `libs/data.ts` — данные и колонки, общие для всех: детерминированный генератор,
  20 колонок, `name` — строка, остальные — числа.
- `libs/<библиотека>.ts` — таблица библиотеки и селекторы её чекбокса «выбрать все» и
  заголовка сортировки. Новая библиотека — новый файл и строка в `main.ts`.
- Ориентиры без готовой таблицы: `plain` — голый Vue (`libs/PlainTable.vue`: `v-for`,
  нативные чекбоксы, выбор в реактивном `Set`), `tanstack` и `reka` — TanStack Table v9
  (`libs/TanstackTable.vue`) с нативными чекбоксами и с `CheckboxRoot` из Reka UI (так
  устроена Data Table shadcn-vue).
- `core` — опыт «ядро без проводки» (`libs/CoreTable.vue`): коллекция таблицы soldy
  (`TTableCollectionFacade`, фасады строк, их `cells`), а рисует её голый `v-for` без
  компонентов строк, адаптерных контекстов и обмена.
- Флаги участника — через «+»: `virtual` — окно (таблица в обёртке `Virtual`), `mode=none` — без выбора (сценарии
  выбора пропускаются), `cols=5` — только первые колонки. У soldy ещё `reorder` — колонки можно переставлять
  (`reorderable`), и после сортировок идут три сценария перестановки: «Взять колонку», «Смена места» и «Отпустить»
  (замер — пока колонка не встала); `preview=column` — за жестом идут и ячейки строк (`reorderPreview: 'column'`),
  `preview=none` — шапка стоит (`reorderPreview: 'none'`); `motion=reduce` — без движения (`useMotion('reduce')`);
  `fit=contain` — гибкие колонки ровно заполняют место (`columnFit: 'contain'`): таблица не шире места, и окно
  таблицы вбок не прокручивается; `fit=none` — колонки шириной по умолчанию, 160 px, место они не делят
  (`columnFit: 'none'`). Без него — `auto` по умолчанию: колонки растут от 160 px, и 20 колонок шире окна
  стенда — окно таблицы прокручивается вбок (раздел «где платит таблица»). `width=3248` — таблица в обёртке
  такой ширины, px: 3248 — сумма 20 колонок по 160 px и колонки выбора, колонки влезают в место, и окно
  таблицы вбок не прокручивается в любом `columnFit` (вбок прокручивается страница). `track` — состав сверяется по ключу записи (`trackBy` по `data.id`): замена данных обновляет
  строки, а не пересобирает их. Без флагов таблица и сценарии те же.
- Страниц две: `index.html` (`main.ts`) — участники на Vue, `react.html` (`react.tsx`) — на React; у
  прогонщика участник React пишется с префиксом `react:` (`react:soldy+fit=contain`), флаги те же. Таблица
  участника React — `libs/react/<библиотека>.tsx`: компонент `Bench` над строками и селекторы. Строки
  страница отдаёт перерисовкой корня (`root.render`), пустые — пустым корнем.
- Участники React: `soldy` — адаптер React, флаги и тема общие с Vue (`libs/soldy-setup.ts`); `plain` —
  голый React (`map`, нативные чекбоксы, выбор в `Set` состояния); `shadcn` — Data Table shadcn/ui: TanStack
  Table v9 и чекбоксы Radix, без классов Tailwind; `mui` — MUI `Table` по примеру «Sorting & selecting»
  (`DataGrid` бесплатно показывает не больше 100 строк на страницу); `antd` — Ant Design `Table` с
  `rowSelection` и `sorter`, без страниц, `virtual` — его окно на 800 px; `mantine` — Mantine `Table` и
  `Checkbox` по примерам «Table with selection» и «Sort table».
- `bench.ts` — сценарии (`window.bench`), общие для обеих страниц; `run.mjs` — прогонщик и итоговая таблица.

## Методика

- Продакшн-сборка, Chromium (Playwright), окно 1600×1000. Новая страница на каждый
  прогон, в таблице — медиана. С 2026-10-15 прогонщик печатает рядом разброс прогонов
  (min–max), у времени — до успокоения.
- Время — от действия до момента, когда кадры снова идут чаще, чем раз в 50 мс, три
  кадра подряд: в него входят асинхронные досчёты библиотеки, а не только первый кадр.
- Действия — настоящие клики в DOM: чекбокс «выбрать все» в шапке, заголовок первой
  колонки. Перестановка — события указателя мыши из кода (`PointerEvent`) по заголовку
  второй колонки: нажатие и протяжка за порог жеста, шаг за середину третьей,
  отпускание.
- Память — прирост `usedJSHeapSize` после принудительной сборки мусора. «Память после»
  с 2026-10-15 мерится ещё и после сборки вне стека (`gc({ execution: 'async' })`):
  сборка `gc()` из скрипта страницы оставляет живым то, на что указывает её стек вызова,
  и для поиска утечек не годится (раздел «память после замены по ключу и
  размонтирования»).
- У всех настройки по умолчанию, виртуализация выключена, ячейки — текст без своих
  рендереров. Прогонщик проверяет, что действие выполнилось: число отмеченных строк и
  первая строка после сортировки.

5000 строк × 20 колонок, 3 прогона. soldy — `main` на `453465a7`.

| Память после рендера | 729 МБ       | **409 МБ**      | 2,8 ГБ         |
| Выделить все         | **1,7 с**    | 2,5 с           | 11,2 с         |

| Сортировка ↑         | **1,5 с**    | 2,0 с           | 10,1 с         |
| Сортировка ↓         | **1,7 с**    | 2,0 с           | 9,1 с          |
| Замена данных        | **4,5 с**    | 5,1 с           | 11,1 с         |
| Размонтирование      | 0,45 с       | **0,27 с**      | 11,3 с         |
| DOM-узлов            | **125 тыс.** | 145 тыс.        | 130 тыс.       |

**Element Plus 2.14.7** замерен один раз и из стенда убран: рендер 9,1 с, память
580 МБ, «выделить все» 41 с, сортировка 46–91 с, замена данных 60 с. Прогон шёл
минутами и ничего не добавлял к сравнению.

Выводы:

- По скорости действий soldy впереди; в первом рендере на 0,5 с впереди Naive UI.
- Отставание одно — память: Naive UI держит ту же таблицу в 1,8 раза легче. У нас около
  146 КБ на строку, утечки нет (после размонтирования куча возвращается).
- Сортировка у нас почти целиком — пересчёт стилей и раскладки браузера после
  перестановки 5000 строк, наш JS там мал. Лечится только сокращением DOM.

Оговорки: одна машина, три прогона. Разница в 0,5 с близка к шуму, разница в разы — нет.
Первый клик сортировки у Naive UI — по убыванию, это её порядок. Память «после
размонтирования» у других библиотек (350–2260 МБ против наших 37) не сравнивается:
похоже на их кэши, а не на утечку — не исследовали.

- Память — на 14 МБ меньше, хотя у каждой строки добавился компонент: таблица без слота
  больше не пробрасывает его строкам, и у каждой ячейки на один фрагмент слота меньше —
  минус 100 тыс. vnode и вдвое больше пустых текстовых узлов-якорей.
- Рендер, замена данных и размонтирование — в пределах шума.
- В профиле первого рендера около 0,5 с из 3 — сборка маршрутов событий при
  монтировании каждого компонента: участника события ищут перебором всех пропсов и
  триггеров. Задача — [869feqa1t](https://app.clickup.com/t/869feqa1t).

  ([869feq9un](https://app.clickup.com/t/869feq9un)). Снятие выделения и сортировка ничего

## 2026-10-09 — Vue, шина платит за подписку, обмен — один слушатель на участника

[869ff057c](https://app.clickup.com/t/869ff057c), PR
[#368](https://github.com/youra-h/soldy/pull/368). Пересмотр механизмов обмена и
событий, согласованный с владельцем:

- **шина ядра** (`TEvented`) заводит эмиттер, перехватчики, слушателей и пробросы при
  первом использовании и снимает с последней отпиской — шина без подписчиков стала
  одним объектом;
- **обмен** слушает шину каждого участника одним слушателем всех событий
  (`TEvented.listen`), общим для состояния и событий, а не маршрутом `on` на каждое
  событие поверхности и подпиской на каждый триггер свойства. Что делать с событием,
  говорит таблица маршрутов типа — одна на все монтирования;
- ячейки состояния и входов обмена без подписчиков: порт действует по ответу `set()`.

## 2026-10-10 — Vue, жест перестановки в `head` — как до живой перестановки

[869ffc5mv](https://app.clickup.com/t/869ffc5mv) и [869ffap5j](https://app.clickup.com/t/869ffap5j),
PR [#388](https://github.com/youra-h/soldy/pull/388). После живой перестановки (раздел выше) жест в
`head` на 5000 строк × 20 колонок без окна стоил вдвое дороже прежнего: взять колонку — 1,15 с против
0,53, смена места — 0,40 с против 0,16. Куда уходит время, показала трасса жеста — новый скрипт
стенда `npm run trace` (см. «Стенд»). Причин три.

1. **Пересчёт стилей в обработчике указателя.** Плагин жеста писал корню ширину взятого — наследуемую
   переменную, то есть новый стиль всем 125 тыс. элементам, — а следом читал стиль корня (направление
   строки) и его коробку. Браузер пересчитывал стиль синхронно, прямо в обработчике (~260 мс), и ещё
   раз в кадре — там его будит курсор «тащу» на корне по `:has()`, он есть и до живой перестановки.
   Теперь ширина лежит там, где её читают: на шапке в `head` (тело её не читает), на корне — только в
   `column`; в обработчике сначала чтения — снимок, направление строки, место, — потом записи, а
   направление строки берётся из снимка.
2. **Перестройка слоёв (`Layerize`) ~350 мс на взятии и на каждой смене места.** Чекбокс строки
   (`relative`) и его поле (`z-10`) рисовались после заголовков, и заголовок, ставший своим слоем, —
   сосед с переходом сдвига, приземление взятого, — сверялся на каждой перестройке слоёв с каждым из
   них. Проверка: без колонки выбора (`soldy+reorder+mode=none`) `Layerize` смены места — 0 мс,
   взятия — 17. Теперь шапка поднята над телом всегда (`relative z-30`, как была у закреплённой) и
   рисуется после тела (`packages/themes/oren/AGENTS.md`, «Слой в шапке платит за всё
   позиционированное в теле»). `will-change` на заголовках — запасной путь — не понадобился.
3. **Линия места перекладывала таблицу** (869ffap5j). Без движения и в `none` линия появлялась и
   пропадала вместе с меткой `data-drop` — новый узел в раскладке фиксированной таблицы, ~35 мс
   раскладки на каждую смену места. Теперь линия нарисована у невзятых заголовков весь жест,
   прозрачной, а метка только красит её и ставит к краю.

### Почему отрисовка — вся таблица

Окно (`div.so-table__viewport`) высотой во всю таблицу. Пока колонки влезают, оно ничего не стоит:
`overflow-x: clip` контейнером прокрутки его не делает. Колонки шире места
(`data-overflow='true'`) — окно прокручивается вбок, а область отрисовки у прокрутки, которую
пользователь может прокрутить и у которой есть что прокручивать, Chromium начинает со всей её
коробки, без оглядки на предков: `CullRect::ApplyScrollTranslation` в
`third_party/blink/renderer/platform/graphics/paint/cull_rect.cc` — «Always start from the container
rect, i.e. ignore ancestor clips». Коробка окна — вся таблица: у события `Paint` таблицы в трассе
«выделить все» область — 3248 × 200039 px, все 5000 строк. Без прокрутки окна область — полоса у
экрана с запасом Chromium: у `57419a1f` 3408 × 3192 px, со сверкой (а) 3248 × 3352, около
восьмидесяти строк. Любая перерисовка таблицы — выбор, сортировка, шаг ручки, взятие колонки —
перерисовывает в окне все строки.

## 2026-10-11 — Vue, на равных: с прокруткой вбок и без

[869ffdear](https://app.clickup.com/t/869ffdear), PR
[#394](https://github.com/youra-h/soldy/pull/394). С #382 у таблицы soldy новое свойство: колонки
шире места она прокручивает вбок своим окном, и прокрутка стоит отрисовки (раздел выше). Поэтому
сравнение с другими библиотеками — на равных, в двух случаях: у таблицы есть горизонтальная прокрутка
и её нет. Участники — `plain`, `tanstack`, `reka`, `naive`, `prime`; Element Plus из стенда исключён
(«исходная точка»), `core` — опыт, а не библиотека, и в сравнение не идёт.

### Проверка: у кого прокрутка вбок

таблицу держит не каждый прогон, см. ниже.

**Vue: остаток сборки, а не утечка.** Снимок после размонтирования (он сам собирает мусор до конца) не
находит ни строк, ни записей, ни других экземпляров таблицы — ни с ключом, ни без, при 1, 5 и 10 заменах,
через 2 с после размонтирования и с `motion=reduce`: отложенная работа (анимация, таймер) ничего не
держит. Пережили только описания компонентов на модуле (`TRouting` ×14, `TSurface` ×6, `TPropSpec` ×6):
они заводятся при первом монтировании и от строк не зависят. Разницу даёт сама сборка: `gc()`, позванная
из скрипта страницы, оставляет живыми около 4 МБ снятого. Повторный `gc()` их не снимает, `gc()` из
таймера — не всегда, а сборка отдельной задачей (`gc({ type: 'major', execution: 'async' })`) и сборка
DevTools (`HeapProfiler.collectGarbage`) снимают каждый раз. Отличаются они стеком: отдельная задача
собирает с пустым, а Chromium просматривает стек вызова сборки консервативно, и ячейка, похожая на
указатель на снятый DOM-узел, держит его поддерево с обёртками. Пробник выборки кучи
(`HeapProfiler.startSampling`) после `gc()` видит живыми именно обёртки узлов, созданные монтированием
таблицы. Почему с ключом остаток больше, не разбирали: замена с ключом правит строки на месте, путь у неё
другой. Вне стека с ключом памяти даже меньше — 2,7 МБ против 3,1–3,2.

**React: таблица переживала размонтирование целиком — с ключом и без.** Снимок с ключом после одной
замены: 5000 `TTableRow`, 30 183 `TEvented`, 10 000 записей — по две на строку: данные строк и первые
`items`, — JS-куча +20,2 МБ, 4,1 КБ на строку. Цепочка удерживающих, сокращённо:

```
<div id="app">.__reactContainer$… → FiberNode → FiberRootNode
  .onUncaughtError → область модуля React DOM ::return_targetInst → FiberNode
  .ref → ref корня адаптера (useAdapter) → область его рендера
    ::adapter → TAdapterContext …
    ::props → {ctrl, children} .children → ::facade → TTableCollectionFacade
      .engine → TCollectionEngine ._driver ._storage ._items → TTableRow
```

React DOM помнит узел своего дерева, на который пришло последнее событие (`return_targetInst`), до
следующего события на странице. У снятого узла React чистит пропсы, состояние и эффекты, но не `ref`.
Ref корня адаптера был замыканием на контекст и на область своего рендера — пропсы и связку, — и через
них держал всю таблицу. В снимке узел последнего события — заголовок колонки: сценарий кончается
сортировками по нему. Держит до следующего события: в части прогонов оно успевает раньше замера, отсюда
разброс (2,6–20,6 МБ вне стека) и снимки без переживших — таблицу держали 7 снимков из 14. С числом
замен не растёт: при пяти заменах держится та же одна таблица.

Исправлено в адаптере React (`useAdapter`): ref корня отпускает контекст, когда тот уничтожен, и заведён
вне области `useAdapter`, чтобы не держать её пропсы и связку. Сторож —
`ui/react/__tests__/root-ref-lifetime.spec.tsx`: таблица с `trackBy`, замена по ключу, размонтирование
— ни один ref, который React оставил узлам таблицы, до контекстов не доходит; до исправления —
12 обращений. После исправления у React вне стека 2,5 МБ во всех 20 прогонах, а 10 снимков из 10
переживших не находят. Цена — слушатель на шине каждого контекста: после рендера 197,7 МБ против 197,2.

| Пережили размонтирование, шт | Vue  | Vue, `track` | React, `track`, до | React, после | React, `track`, после |
| ---------------------------- | ---- | ------------ | ------------------ | ------------ | --------------------- |
| `TTableRow`                  | 0    | 0            | 5000               | 0            | 0                     |
| записи строк                 | 0    | 0            | 10 000             | 0            | 0                     |

**Пока таблица смонтирована**, записей в куче после замен (500 строк, снимок): у Vue 500 при любом числе
замен, у React — 1500 и после двух замен, и после пяти. Это данные приложения, пропсы прошлого рендера
(React держит их во втором дереве до следующего рендера) и пропсы сборки: контекст адаптера помнит их
всю жизнь монтирования (`TAdapterContext.props`). С заменами не растёт; пропсы сборки —
[869fhd7w7](https://app.clickup.com/t/869fhd7w7), правка механики setup.

### Вывод

- **Утечки по ключу нет.** Разница «Памяти после» с ключом и без — остаток сборки `gc()` из скрипта
  страницы: его держит стек вызова сборки, а не страница. Вне стека Vue — 2,7 МБ с ключом против 3,2 без,
  React — 2,5 вровень. «Память после» из одной сборки `gc()` утечку не показывает, поэтому прогонщик
  мерит её и вне стека.
- **React держал размонтированную таблицу целиком до следующего события на странице** — с ключом и без,
  через ref корня на узле последнего события. Исправлено в адаптере React, сторож — тест на ref'ы узлов.
- Ни у Vue, ни у React память после размонтирования не растёт — ни с числом замен, ни со временем.

После правки — через приёмник событий связки (`useExchange`). Эффект событий ставится один раз, его

держит область хука, а в ней фабрику первого рендера (`::factory` → `::props`). Опыт, в ветке его нет: с
