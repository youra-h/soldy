# ТЗ: общий слой адаптеров (`@soldy/setup`) — реализация с нуля

Документ — единственный источник требований к слою, который стоит между ядром
soldy и шестью UI-адаптерами. Прежняя реализация слоя удалена целиком, и
восстанавливать её не нужно: задача — спроектировать слой заново, опираясь на
требования ниже, на опыт соседних слоёв репозитория и на известные приёмы
проектирования.

Как читать:

- **«Дано»** (раздел 3) — то, что уже есть и меняться не должно: ядро, плагины,
  дескрипторы компонентов, компоненты адаптеров, API приложения. Это входы.
- **«Требуется»** (разделы 4–7) — что слой обязан делать. Описано поведение и
  контракты на границах, а не внутреннее устройство: классы, модули, имена
  внутренних сущностей и их количество выбирает исполнитель.
- **«Сценарии приёмки»** (раздел 8) — граничные случаи, каждый из которых
  когда-то был багом. Реализация, которая их не проходит, не принята.

Имена в `моноширинном` шрифте, про которые сказано «заморожено», менять нельзя:
ими пользуется код, который остаётся. Всё остальное — на усмотрение исполнителя.

---

## 1. Контекст

soldy — headless UI-библиотека. Состояние и поведение компонента живут вне
фреймворка, а фреймворк только рисует и пробрасывает ввод.

| Слой                  | Что делает                                                                                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core`       | Модели компонентов: классы с пропсами, событиями и вычисляемыми свойствами. Ничего не рендерит.                                                             |
| `packages/plugins`    | Поведение, которому нужен DOM и жизненный цикл: клавиатура, фокус, позиционирование, «нажали мимо». Ставятся в набор плагинов компонента.                   |
| **общий слой**        | **Предмет ТЗ.** Всё, что у шести адаптеров одинаково: описание компонента, его сборка на монтирование и обмен значениями с фреймворком.                     |
| `packages/ui/*`       | Адаптеры: Vue (полный порт, 32 компонента), React, Solid, Svelte, Angular, Web Components (базовый набор). Единственное место, где импортируется фреймворк. |
| `packages/themes/*`   | CSS и плагины, без которых CSS темы не работает.                                                                                                            |
| `packages/icons/*`    | Пакеты иконок — реализации закрытого списка ролей.                                                                                                          |
| `packages/playground` | Стенд: рисует компоненты всеми пропсами, читает метаданные дескрипторов.                                                                                    |

Два правила границ, которые определяют смысл слоя:

1. **Общий слой, ядро и плагины не импортируют фреймворки** — ни `vue`, ни
   `react`, ни типы вроде `Ref` и `PropType`.
2. **В адаптере нет логики.** Адаптер — проводка: куда положить значение, как
   отдать событие, в какой момент своего цикла это сделать. Признак нарушения:
   написанное пришлось бы повторить в пяти других адаптерах. Всё, что
   повторялось бы, живёт в общем слое. «Адаптер решает, _куда_ положить
   значение; _когда_ и _в каком порядке_ — общий слой.»

Компонентом управляют с двух сторон, и они обязаны быть равнозначны:
декларативно из разметки (`<Button text="x" @change:text="…" />`) и императивно
через инстанс ядра (`btn.text = 'x'`, `btn.events.on('change:text', …)`), в том
числе когда инстанс создан снаружи и передан компоненту пропом `ctrl`.

## 2. Условия задачи

- Удалены: `packages/setup` целиком, кроме `packages/setup/descriptors/` и
  части тестов (приложение А), и `packages/accessor` целиком.
- Точка входа `@soldy/setup` обязана существовать: из неё импортируют
  дескрипторы, компоненты адаптеров, темы, стенд и приложения. Нужен ли второй
  пакет (раньше рефлексия свойств жила отдельно, в `@soldy/accessor`), решает
  исполнитель и обосновывает; манифесты воркспейса и конфиг changesets правятся
  соответственно.
- Удалённый код не восстанавливается из истории git и не берётся за образец.
- Разделы `AGENTS.md` и `docs/architecture.md`, описывающие прежнее устройство
  слоя, требованиями не являются. Правила репозитория из `AGENTS.md`, не
  связанные с устройством слоя (границы слоёв, «никаких костылей», нейминг,
  версии, a11y, коллекции ядра), действуют в полной мере.
- Компоненты адаптеров (`packages/ui/*/src/components/**`) **заморожены**.
  Адаптерный слой (`packages/ui/*/src/adapter/**`, около десяти файлов на
  фреймворк) исполнитель переписывает под свой API, сохраняя то, что этот слой
  отдаёт компонентам (раздел 3.5).

## 3. Дано (входы, менять нельзя)

### 3.1 Класс компонента ядра

Всё, что общий слой знает о компоненте, он узнаёт из класса ядра и дескриптора.

- **Конструктор** — `new Ctor(props?, options?)`. `props` — объект интерфейса
  пропсов (`IButtonProps`), `options` — служебные аргументы (у фасада коллекции
  — владелец и готовый движок).
- **Тип пропсов выводится из класса.** Класс реализует `IEntity<TProps>`;
  интерфейс пропсов вторым местом нигде не записывается.
- **Проп — геттер и сеттер инстанса.** Сеттер эмитит `change:<имя>` на шине
  инстанса. Сеттер не обязан проверять «то же значение»: часть сеттеров эмитит
  и на повторе.
- **Шина событий** — `instance.events`, типизированная закрытой картой
  (`TButtonEvents`). Подписка — `on(name, handler)` / `off(name, handler)`. У
  объекта без поля `events` шиной может быть он сам; объект без `on`/`off` —
  не источник событий.
- **Вычисляемые свойства** инстанс отдаёт только на чтение: `present`,
  `classes`, `aria`, `dataset`, `attrs` и другие. О смене сообщает событие
  (`change:classes`). Составное значение пересекает границу **снимком**: либо
  у объекта есть свой `valueOf()`, возвращающий новый простой объект или массив
  на каждый вызов (`TClasses` → `string[]`), либо владелец заменяет объект
  целиком. Мутация на месте запрещена — адаптер узнаёт об изменении по смене
  идентичности.
- **Умолчания** — `static defaultValues` класса: значение, с которым стартует
  незаданный проп. **Значим ключ, а не значение**: `closable: undefined`
  означает «умолчание объявлено и равно `undefined`» (у элемента Tabs — «как у
  владельца»). Проверка `value !== undefined` вместо проверки наличия ключа —
  ошибка. Наследник вправе переопределить умолчание родителя (`visible` у
  Frame — `false`, у базового визуального слоя — `true`).
- **Служебные события** объявлены в карте ядра, но эмитит их общий слой:
  `bundle:create` (аргумент — набор плагинов), `plugin:event` (аргумент —
  конверт `{ name, args }`, тип `TPluginEvent`). У владельцев коллекций ядро
  само шлёт `engine:create`.
- **Внешний инстанс** (`ctrl`) может жить дольше компонента и быть передан
  повторно. Всё, что слой на него повесил, снимается при размонтировании.

### 3.2 Плагины

- Плагин — класс без аргументов конструктора: `install(ctx, options?)`,
  `created()`, `destroy()`, своя шина `events`. Пропсы плагина — его геттеры и
  сеттеры с событиями `change:<имя>` на шине плагина; вычисляемые значения —
  геттеры (`styles`, `ownerAttribute`). Умолчания — `static defaultValues`
  класса плагина, с тем же правилом «значим ключ». Тип опций — второй параметр
  `install` конкретного класса.
- `TPluginBundle(instance)` — набор плагинов одного компонента:
  `use(Ctor, options?)`, `get(Ctor)`, `remove(Ctor)`, `getInstance()`,
  `created()` (объявляет плагины готовыми, в порядке установки; плагин,
  поставленный после, объявляется сразу в `use`), `destroy()` (в обратном
  порядке), флаг `destroyed`, шина `events` с событиями `use` и `remove`
  (аргументы — класс и экземпляр плагина).
- `PLUGIN_EVENTS` — список событий базы плагина, которые публикуются наружу
  (сейчас это `create`). В объявление плагина он подмешивается **явно**;
  события базы вне списка (`install`, `destroy`) — внутренняя механика набора и
  наружу не выходят ни в рантайме, ни в типах.
- `TElementPlugin` — плагин с полем `element`: корневой DOM-узел компонента.
  Остальные плагины берут узел у него.

### 3.3 Коллекции ядра

Компонент-владелец (`TTabs`) коллекцию не держит. Её держит **фасад**
(`TTabsCollectionFacade`) — отдельный класс ядра с конструктором
`(props, { owner, engine? })`: дали готовый движок — работает на нём, не дали —
собирает свой. У фасада есть поле `engine`, свои пропсы (`items`, `trackBy`,
вычисляемые `shown`, `activeItem`) и события (`item:added`, `change:count`, …).

У элемента так же: компонент (`TTabsItem`) и **фасад элемента**
(`TTabsItemCollectionFacade`) с методом `setContext(itemContext)`; контекст
элемента выдаёт `TItemContextRegistry(engine.getCore()).get(item)`. Фасад
элемента отдаёт пропсы членства: `active`, `order` и подобные.

Движок расширяется: `engine.use(extension)`, установленные расширения —
`engine.extensions[имя]`. Общему слою нужны `plain` (`push`, `remove`, шина с
`item:added`), `batch` (`items`), `meta` (`apply(item, значения)`). Плагины
коллекции: `TCollectionBundlesPlugin` (`bindEngine(engine)`,
`register(bundle, item)`) и `TDragPlugin` (`activate(engine)`).

### 3.4 Дескрипторы (`packages/setup/descriptors/`) — заморожены

Дескриптор — описание типа компонента: класс ядра, родитель, объявление
(пропсы, события, слоты) и плагины. **Синтаксис ниже заморожен**: папка
остаётся как есть, и новая реализация обязана его принять. Откуда дескрипторы
импортируют функции описания, решает исполнитель — пути импорта в этих файлах
поправить можно, содержимое объявлений нельзя.

Обычный компонент и цепочка наследования:

```ts
export const ButtonDescriptor = defineDescriptor(() =>
  defineComponent({
    ctor: TButton,
    extends: TextableDescriptor(),
    contribution: {
      props: {
        view: { type: String, triggers: ['change:view'] },
      },
      slots: {
        leading: { description: 'Перед текстом' },
        default: {
          scope: { text: defineType<string>(String) },
          description: 'Содержимое кнопки. Задано — переопределяет проп text',
        },
        trailing: { description: 'После текста' },
      },
    },
  }),
)
```

Цепочка у кнопки: Entity → Component → ComponentView → Stylable → Control →
Textable → Button. Корень (`EntityDescriptor`) класса ядра не имеет: он
объявляет то, что принадлежит связке адаптера с инстансом, — пропсы `ctrl`,
`embedded`, `pluginProps` и события `bundle:create`, `plugin:event`. Визуальный
слой добавляет видимость, наборы атрибутов и плагины:

```ts
export const ComponentViewDescriptor = defineDescriptor(() =>
  defineComponent({
    ctor: TComponentView,
    extends: ComponentDescriptor(),
    contribution: {
      slots: { default: { description: 'Содержимое компонента' } },
      props: {
        visible: { type: Boolean, triggers: ['change:visible'] },
        present: {
          type: Boolean,
          protected: true,
          triggers: ['change:rendered', 'change:visible'],
        },
        tag: { type: [String, Object], triggers: ['change:tag'] },
        classes: { type: Object, protected: true, triggers: ['change:classes'] },
        // …
      },
      events: ['show', 'hide', 'show:before', 'show:after', 'ready'],
    },
    plugins: [ElementPluginDescriptor, ReadyPluginDescriptor],
  }),
)
```

Объявление пропа: `type` — конструктор рантайма или массив конструкторов
(`String`, `[String, Object]`); `protected: true` — свойство вычисляет владелец,
снаружи его только читают; `triggers` — события владельца, после которых
значение надо перечитать; необязательные `get(instance)` / `set(instance,
value)` — нетривиальные чтение и запись вместо `instance[name]`. Проп без
триггеров — сквозной (`ctrl`, `engine`): в ядро пишется, наружу не отдаётся.

Объявление плагина — один раз, константой модуля; опции установки задаёт
дескриптор, который плагин ставит:

```ts
export const DismissPluginDescriptor = definePlugin({
  ctor: TDismissPlugin,
  namespace: 'dismiss',
  contribution: {
    events: [...PLUGIN_EVENTS, 'dismiss'],
    props: {
      enabled: { type: Boolean, triggers: ['change:enabled'] },
      ownerAttribute: { type: Object, protected: true, triggers: ['create'] },
    },
  },
})

// в дескрипторе Popover
plugins: [AriaPluginDescriptor, DismissPluginDescriptor.with({ focusOutside: true })]
```

Компонент с коллекцией описывается **парами дескрипторов**: свои пропсы
компонента отдельно, членство в коллекции отдельно.

```ts
// Владелец: свои пропсы, слоты и плагины
export const TabsDescriptor = defineDescriptor(() =>
  defineComponent({
    ctor: TTabs,
    extends: ControlDescriptor(),
    contribution: {
      slots: {
        default: { description: 'Табы — элементы коллекции' },
        content: { description: 'Панели табов' },
        item: { scope: { item: defineType<ITabsItem>(Object) } },
      },
      props: {
        orientation: { type: String, triggers: ['change:orientation'] },
        closable: { type: Boolean, triggers: ['change:closable'] },
      },
    },
    plugins: [
      CollectionBundlesPluginDescriptor,
      CollectionElementsPluginDescriptor,
      TabsKeyboardPluginDescriptor,
      DragPluginDescriptor,
    ],
  }),
)

// Общая база владельцев коллекций — без класса ядра
export const CollectionDescriptor = defineDescriptor(() =>
  defineComponent({
    contribution: {
      props: {
        engine: { type: Object },
        items: { type: Array, triggers: ['change:items'] },
        shown: { type: Array, protected: true, triggers: ['change:shown'] },
        trackBy: { type: Function, triggers: ['change:trackBy'] },
      },
      events: ['engine:create', 'item:added', 'item:removed', 'change:count' /* … */],
    },
  }),
)

// Коллекционная часть владельца — фасад
export const TabsCollectionDescriptor = defineDescriptor(() =>
  defineComponent({
    ctor: TTabsCollectionFacade,
    extends: CollectionDescriptor(),
    contribution: {
      props: {
        activeItem: { type: Object, protected: true, triggers: ['change:activation'] },
      },
      events: ['item:activated', 'item:deactivated', 'item:close'],
    },
  }),
)

// Коллекционная часть элемента — фасад элемента; проп с собственным чтением
export const TabsCollectionItemDescriptor = defineDescriptor(() =>
  defineComponent({
    ctor: TTabsItemCollectionFacade,
    contribution: {
      props: {
        active: { type: Boolean, triggers: ['change:active'] },
        order: { type: Number, protected: true, triggers: ['change:order'] },
        tab_closable: {
          type: Boolean,
          protected: true,
          get: (item: TTabsItemCollectionFacade) => item.closable,
          triggers: ['change:closable'],
        },
      },
    },
  }),
)
```

Общий фрагмент пропсов нескольких компонентов (`LIST_PROPS` у ListBox и Select)
— константа, подмешиваемая спредом в `props`; объявлена через `satisfies
Record<string, IComponentPropDefinition<keyof TListEvents>>`, и имена её
триггеров обязаны дойти до типов событий дескриптора.

Замороженные имена описания: `defineDescriptor`, `defineComponent`,
`definePlugin` (и метод `.with(options)` у его результата), `defineType`, тип
`IComponentPropDefinition<TEventName>`.

### 3.5 Компоненты адаптеров — заморожены

Компонент зовёт фабрику контекста, подключает расширения и отдаёт контекст
хуку адаптерного слоя. Дженериков компонент не пишет нигде.

Vue, обычный компонент:

```ts
// base.component.ts — статический слой, выполняется при импорте модуля
export const emitsButton: TEmits = useEmits(ButtonDescriptor())
export const propsButton: TProps = useProps(ButtonDescriptor()) as TProps
export type ButtonProps = UseProps<typeof ButtonDescriptor, IButton>

// setup.component.ts
setup(props: ButtonProps, { emit }: SetupContext) {
	const adapter = createVueAdapterContext(ButtonDescriptor(), { ctrl: props.ctrl, props })

	return useAdapter(adapter, props, emit)
}
```

Vue, владелец коллекции — два контекста на одном наборе плагинов:

```ts
setup(props: TabsProps, { emit }: SetupContext) {
	const adapter = createVueAdapterContext(TabsDescriptor(), { ctrl: props.ctrl, props })
	const refs = useAdapter(adapter, props, emit)

	const collectionAdapter = createVueAdapterContext(
		TabsCollectionDescriptor(),
		{ props, options: { owner: adapter.instance, engine: props.engine } },
		{ bundle: adapter.bundle },
	)
		.use(TCollectionExtension, { elevator: VueElevatorFactory })
		.use(TDragAndDropCollectionExtension, { elevator: VueElevatorFactory })

	const refsCollection = useCollectionAdapter(collectionAdapter, props, emit)

	return { ...refs, ...refsCollection }
}
```

Vue, элемент коллекции:

```ts
const adapter = createVueAdapterContext(TabsItemDescriptor(), { ctrl: props.ctrl, props })

const itemAdapter = createVueAdapterContext(
  TabsCollectionItemDescriptor(),
  { props },
  { bundle: adapter.bundle },
).use(TCollectionItemExtension, { item: adapter.instance, elevator: VueElevatorFactory })

return {
  ...useAdapter(itemAdapter, props, emit),
  ...useAdapter(adapter, props, emit),
  context: itemAdapter.instance.context,
}
```

Остальные фреймворки:

```ts
// React: контекст держит хук адаптера, он же пересобирает его под StrictMode и <Activity>
const adapter = useAdapterContext(() =>
  createAdapterContext(ButtonDescriptor(), { ctrl: props.ctrl, props }),
)
const { ctrl, plugins, ref, forwardProps, state } = useAdapter(adapter, props)

// Solid, Svelte: то же без useAdapterContext; у Svelte пропсы — функцией
useAdapter(createAdapterContext(ButtonDescriptor(), { ctrl: props.ctrl, props }), props)

// Angular, Web Components: функция setup компонента
const adapter = createAdapterContext(ButtonDescriptor(), { ctrl, props })
return useAdapter(adapter) // Angular
return useAdapter(adapter, host, onUpdate) // Web Components
```

Что адаптерный слой отдаёт компонентам (форма результата заморожена,
реализация — нет):

| Фреймворк      | Компонент получает                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vue            | Плоский объект для шаблона: `ctrl`, `plugins`, `rootElement` (есть, только если в наборе `TElementPlugin`) и по рефу на каждое свойство с триггерами. `useCollectionAdapter` — то же без `ctrl` и `rootElement`. Статика: `useProps`, `useEmits`. Ещё: `useIcon(role)`, `useSplitAttrs()`, `VueElevatorFactory`, типы `UseProps`, `TProps`, `TEmits`, `SetupContext`. `createVueAdapterContext` — та же фабрика контекста, снимающая Vue-прокси с `ctrl` и со значений `options`. |
| React          | `{ ctrl, plugins, ref, forwardProps, state }`; `useAdapterContext(factory)`; `renderSlot`, `toAriaProps`; типы `UseProps`, `UseDomProps`, `EventProps`.                                                                                                                                                                                                                                                                                                                           |
| Solid          | `{ ctrl, plugins, ref, forwardProps(), state }`; `renderSlot`; те же типы.                                                                                                                                                                                                                                                                                                                                                                                                        |
| Svelte         | `{ ctrl, plugins, attachElement, forwardProps, state }`; те же типы.                                                                                                                                                                                                                                                                                                                                                                                                              |
| Angular        | `TBinding<TInstance>`: `state` (сигнал), `ctrl`, `plugins`, `syncInputs(inputs)`, `syncEvents(outputs)`, `bindElement(el)`, `destroy()`; базовый класс `TComponentBase`. Входы и выходы компонента — статические массивы строк из **закоммиченных сгенерированных файлов** (`npm run generate --workspace=@soldy/ui-angular`).                                                                                                                                                    |
| Web Components | `TBinding<TInstance>`: `state`, `ctrl`, `plugins`, `syncProps(props)`, `bindElement(el)`, `destroy()`; `defineElement`, `defineProps`, `useAttributes`, шаблонные помощники.                                                                                                                                                                                                                                                                                                      |

Из `@soldy/setup` компоненты берут напрямую (имена заморожены):
`createAdapterContext`, дескрипторы, `withParts`, `TCollectionExtension`,
`TCollectionItemExtension`, `TDragAndDropExtension`,
`TDragAndDropCollectionExtension`, `TTabsContentBindingExtension`.

### 3.6 API приложения, темы, иконок и стенда — заморожено

```ts
// Плагины и расширения снаружи
usePlugins(TButton, [TTimerPlugin])
usePlugins(TButton, [{ ctor: TRipplePlugin, options: { ms: 300 } }], { scope: 'all' })
useExtensions(TTags, [(owner) => new TTagsHistoryExtension({ owner })])

// Тема — те же регистрации одним объектом
export default defineTheme({ name: 'oren', plugins: [{ type: TTabs, plugins: [TTabsViewPlugin] }] })
useTheme(oren)

// Иконки
setIcons(material)
setIcons({ close: myCloseIcon })
```

Каждая регистрация возвращает функцию отмены. Иконки: `setIcons`, `getIcon`,
`hasIcon`, `resetIcons`, `missingIconRoles`, константы `ICON_ROLES`
(`check`, `checkIndeterminate`, `close`, `arrowDown`, `arrowRight`),
`MISSING_ICON`, типы `TIconSource` (`{ viewBox, body }`), `TIconRole`,
`TIconPack`. Типы темы: `ITheme`, `IThemePlugins`, `IThemeExtensions`.

Стенд читает метаданные дескриптора: список своих пропсов, список плагинов с их
пропсами, у каждого пропа — имя с неймспейсом, тип, признак `protected`,
триггеры и умолчание с различением «ключа нет» и «ключ есть, значение
`undefined`». Адаптерный файл стенда править можно; сама возможность обязана
остаться (раздел 4.1).

## 4. Требуется: описание компонента

### 4.1 Дескриптор

- `defineDescriptor(build)` отдаёт фабрику; дескриптор строится **один раз на
  тип** при первом вызове, дальше фабрика отдаёт тот же объект. Идентичность
  дескриптора устойчива — по ней допустимо кэшировать всё, что зависит только
  от типа.
- Дескриптор неизменяем. Его декларации делят все монтирования и все
  наследники; попытка изменить их у потребителя не должна затронуть остальных.
- **Наследование (`extends`)**:
  - пропсы и события — родительские, затем свои, в порядке объявления;
  - слот с тем же именем заменяет родительский, оставаясь на его месте (Button
    уточняет `default`, добавляя scope);
  - плагин того же класса заменяет родительский, оставаясь на его месте (так
    наследник меняет опции плагина);
  - класс ядра — свой, а без него родительский; у корня класса нет;
  - **умолчания пропсов пересчитываются от итогового класса**, а не копируются
    у родителя.
- **Умолчание пропа плагина**: опция установки, если она задана (не
  `undefined`), иначе `defaultValues` класса плагина. `.with(options)`
  возвращает новое определение, исходное не меняется — его делят все
  дескрипторы.
- **Имя с неймспейсом.** У пропа и события плагина два имени: сырое (`label` —
  так к нему обращаются у владельца) и полное (`aria:label` — уникальный
  ключ). Два объявления с одним полным именем в составе одного компонента —
  ошибка сборки с понятным сообщением.
- **Интроспекция.** Дескриптор отдаёт: класс; свои (с унаследованными) пропсы,
  события, слоты; плагины; плоские списки всех пропсов и всех событий — свои,
  затем плагинов в порядке плагинов. У декларации пропа читаются имя,
  неймспейс, тип, `protected`, триггеры, умолчание (с различением наличия
  ключа), свои `get`/`set`. Порядок всех списков детерминирован и равен
  порядку объявления: от него зависят закоммиченные метаданные Angular.

### 4.2 Контракт плагина

Контракт — свойство **класса** плагина: пропсы, события, неймспейс. По классу
его можно получить в рантайме — так подключаются плагины, поставленные снаружи
(раздел 6.3). Записывает контракт только объявление `definePlugin`;
использование с опциями (`.with`) его не меняет. Опции одного дескриптора
другому не видны.

### 4.3 Слоты

Слоты — третья категория контракта рядом с пропсами и событиями. Имена слотов
одинаковы во всех фреймворках; единственное преобразование — слот по умолчанию
(`default`) называется `children` у React, Solid и Svelte. `scope` — данные,
которые компонент передаёт внутрь слота, а не ограничение на содержимое. У
плагинов слотов нет. Нужны: имя слота по умолчанию, перевод имени слота в имя
фреймворка, признак «слот со scope», список имён слотов дескриптора.

### 4.4 `withParts`

`withParts(Owner, { Item, Content })` делает части доступными через точку
(`Tabs.Item`). Владелец мутируется намеренно, а не копируется: копия разошлась
бы по идентичности с тем, что экспортирует файл компонента.

## 5. Требуется: имена во фреймворках и статический слой

Ядро и дескриптор говорят на одном языке: `text`, `aria:label`, `change:text`,
`element:ready`. Каждый фреймворк — на своём. Перевод — стратегия, которую даёт
адаптер; применяет её общий слой, одинаково для всех шести.

| Что                   | Ядро / дескриптор | Vue                       | React, Solid, Svelte | Angular          | Web Components  |
| --------------------- | ----------------- | ------------------------- | -------------------- | ---------------- | --------------- |
| Проп компонента       | `text`            | `text`                    | `text`               | `[text]`         | `text`          |
| Проп плагина          | `aria:label`      | `aria_label`              | `aria_label`         | `[aria_label]`   | `aria_label`    |
| Событие компонента    | `change:text`     | `@change:text`            | `onChangeText`       | `(changeText)`   | `change:text`   |
| Событие с частями     | `item:added`      | `@item:added`             | `onItemAdded`        | `(itemAdded)`    | `item:added`    |
| Событие плагина       | `element:ready`   | `@element:ready`          | `onElementReady`     | `(elementReady)` | `element:ready` |
| Двусторонняя привязка | —                 | `update:text` (`v-model`) | —                    | —                | —               |
| Слот по умолчанию     | `default`         | `default`                 | `children`           | без имени        | без имени       |

- **Имя пропа одно во всех фреймворках.** Неймспейс приклеивается через `_`,
  потому что двоеточие — не идентификатор; неймспейс с дефисом переводится в
  camelCase (`icon-styles` + `styles` → `iconStyles_styles`). Проп без
  неймспейса — как есть.
- **Имя события у каждого своё**: Vue и Web Components отдают полное имя ядра;
  React, Solid и Svelte — колбэк-проп `on` + PascalCase по частям, разделённым
  `:` и `-`; Angular — camelCase по тем же частям.
- **Тип-зеркало.** Там, где имя строит функция рантайма, а типы адаптера должны
  дать то же имя (`onChangeText` как ключ пропсов React), нужен парный тип.
  Рантайм и тип обязаны давать одинаковый результат на одних входах; это
  проверяется тестом.
- **Двусторонняя привязка** — свойство фреймворка: у Vue каждый записываемый
  проп с триггерами получает событие `update:<имя пропа>`, плагинные
  включительно (`update:anchor_anchor`). У остальных такого события нет.
- **Публичная поверхность компонента в именах фреймворка** зависит только от
  пары «дескриптор × фреймворк» и считается один раз. В неё входят: пропсы,
  записываемые снаружи, с типом и умолчанием (умолчание — только если его ключ
  объявлен); события — явные, триггеры **всех** пропсов, включая `protected`, и
  события привязки, без повторов и в порядке объявления; имена, которые
  компонент «съедает» (раздел 6.5).
- **Статический слой** объявляет поверхность раньше любого монтирования: Vue —
  `props` и `emits` при импорте модуля; Angular — кодогенерацией в
  закоммиченные файлы; Web Components — `observedAttributes` и свойства
  прототипа. Поэтому поверхность не может зависеть от того, что
  зарегистрировано приложением в рантайме (раздел 6.3).

## 6. Требуется: монтирование и обмен значениями

### 6.1 `createAdapterContext`

Имя, порядок аргументов и ключи опций заморожены — ими пользуются компоненты.

```ts
createAdapterContext(
	descriptor,
	{ ctrl?, props?, options?, embedded? },
	{ bundle? },                          // необязательный третий аргумент
)
```

Вход:

- `ctrl` — готовый инстанс ядра. Нет — инстанс строит класс дескриптора:
  `new Ctor(props ?? {}, options ?? {})`.
- `props` — пропсы фреймворка как есть, **в именах фреймворка** (`aria_label`).
  Сырые имена (`label`) тоже принимаются — для headless-кода и тестов.
- `options` — аргумент конструктора (у фасада — `{ owner, engine }`).
- `embedded` — имя места, если компонент — деталь разметки другого компонента
  (`tags.close`). Не задан — читается из `props.embedded`: проп объявлен у всех
  компонентов, и помнить отдельный шаг не обязан ни один адаптер.
- `bundle` в третьем аргументе — набор, собранный для того же инстанса раньше.
  Так фасад коллекции делит набор с компонентом (раздел 3.5).

Выход — контекст:

- `instance`, `bundle` (или `null`, если плагинов нет), `embedded`, доступ к
  дескриптору и к пропсам, с которыми контекст собран;
- `use(КлассРасширения, опции?)` — подключить расширение контекста, цепочкой;
  `get(КлассРасширения)`. Расширение — класс с конструктором
  `(context, options)`; оно читает у контекста `instance`, `bundle`, `embedded`,
  декларации пропсов дескриптора и пропсы сборки, а на уничтожение
  подписывается через `context.events.on('destroy', …)`;
- `bindElement(el | null)` — связать корневой узел разметки с `TElementPlugin`
  набора. У компонента без этого плагина вызов ничего не делает. Это метод
  контекста, а не расширение: его зовут все шесть адаптеров;
- `destroy()` — эмитит `destroy`, забывает расширения и, если набор собран
  этим контекстом, отвязывает узел **до** уничтожения набора (плагины успевают
  получить `removed`) и уничтожает набор.

Что происходит при сборке, по порядку:

1. **Инстанс** — `ctrl` или конструктор.
2. **Состав плагинов** — плагины дескриптора, затем регистрации приложения для
   этого типа (раздел 6.3). Только если набор собирается здесь.
3. **Набор** — по составу, с опциями. Пустой состав — набора нет.
4. **Объявление набора наружу — на микрозадаче**: сначала `bundle:create` на
   шине инстанса, потом `bundle.created()`. Синхронно нельзя: адаптер
   подписывается на события уже после того, как получил контекст. Набор,
   уничтоженный до микрозадачи (синхронное размонтирование, React StrictMode со
   своим `ctrl`), не объявляется вовсе. Эмит живёт там же, где набор создаётся,
   а не отдельным шагом, который обязан помнить адаптер.
5. **Начальные значения пропсов — здесь и только здесь**, одинаково для всех
   шести адаптеров:
   - свой инстанс получил пропсы конструктором — второй раз не пишутся (сеттер
     `items` фасада пересоздал бы элементы);
   - внешнему `ctrl` пропсы пишутся сеттерами;
   - плагинам пишутся всегда: их создают после инстанса;
   - пишется только то, что **отличается от умолчания** декларации и от
     текущего значения. Проп, равный умолчанию, ничего не задаёт: так внешний
     `ctrl` сохраняет своё состояние, даже когда фреймворк подставил умолчание
     за автора (Vue делает это с каждым пропом, у которого объявлен `default`);
   - порядок: пропсы инстанса, затем плагинов дескриптора, затем плагинов,
     поставленных снаружи.
6. **Чужой набор** (`bundle` в третьем аргументе): состав — только плагины
   дескриптора, регистрации приложения не пересматриваются (иначе фасад получил
   бы плагин реестра второй раз); свойство плагина, которого в наборе нет,
   молча пропускается; начальные значения плагинам не пишутся, плагины снаружи
   не ведутся, набор и узел при `destroy()` не трогаются — всё это делает
   владелец набора. «Свой набор или чужой» — не флаг, который проверяет каждый,
   кто с набором работает.

Набор плагинов снаружи не принимается (кроме описанного деления между
контекстами одного компонента): набор — инвариант компонента, а не его
параметр. Наружу отдаётся доступ к уже созданному — `bundle:create` и
`<неймспейс>:create`.

### 6.2 Обмен значениями на время жизни

Всё ниже — общий слой. Адаптеру остаётся сказать, куда положить значение и как
отдать событие, и выбрать момент своего цикла.

**Ядро → фреймворк (состояние).**

- В состоянии — свойства **с триггерами**, `protected` включительно, под
  именем пропа во фреймворке. Свойство без триггеров — сквозное, следить за ним
  нечем.
- Значение читается у владельца: `get` декларации, а без него `instance[name]`;
  у объекта со своим `valueOf()` берётся снимок.
- **Путь у значения один.** Сработал триггер — свойство перечитывается и
  отдаётся подписчикам. Подписался фреймворк при монтировании — то же самое
  для каждого свойства. Отдельного «стартового снимка» и стартовой записи у
  адаптера нет: инициализация — это и есть подписка.
- **Сначала подписка на триггеры, потом чтение** — порядок держит общий слой,
  иначе изменение между ними теряется.
- Для фреймворков, которые рисуют раньше, чем подписываются (React,
  `useSyncExternalStore`), есть снимок всего состояния: неизменяемый, **тот же
  объект, пока ничего не сменилось**; функции подписки и снимка передаются без
  `this`.
- Составные значения дают новый объект на каждое чтение, поэтому «сменилось ли»
  для простых объектов и массивов сверяется по содержимому (поверхностно), для
  остального — по идентичности.
- Подписка на шину владельца живёт, пока есть хоть один подписчик.

**Фреймворк → ядро (входы).** Фреймворки отдают пропсы тремя способами, и все
три обязаны давать один результат:

| Способ                             | Кто                     |
| ---------------------------------- | ----------------------- |
| по одному пропу, когда он сменился | Vue                     |
| полный набор на каждом проходе     | React, Solid, Svelte    |
| дельта — только изменившееся       | Angular, Web Components |

- **В ядро пишется только то, что поменял фреймворк.** Из полного набора — лишь
  проп, сменившийся с прошлого набора. Иначе повтор откатил бы то, что с тех
  пор поменяли ядро или код через инстанс: список, открытый кликом при
  `open={false}`, закрылся бы от смены плейсхолдера.
- Память «что задал фреймворк» **начинается с пропсов сборки**: первый проход
  пишет только сменившееся с тех пор.
- **`undefined` — два разных случая.** Проп ни разу не задавали — не пишется,
  состояние (в том числе внешнего `ctrl`) остаётся. Проп задавали и сняли —
  возвращается к умолчанию декларации; умолчания нет — значение остаётся. После
  сброса проп снова «не задан».
- В дельте **наличие ключа — уже изменение**. Дельту нельзя обрабатывать как
  полный набор: всё, чего в ней нет, сбросилось бы к умолчанию.
- То же значение не пишется. `protected` не пишется никогда. Значение читается
  по имени во фреймворке, затем по сырому.
- `pluginProps` — обычный вход по всем правилам выше, но приёмник у него другой
  (раздел 6.3). Частный случай не должен быть веткой внутри общего метода.

**События наружу.**

- Пробрасываются явные события и триггеры всех пропсов, `protected`
  включительно, в именах фреймворка.
- **Без повторов** по паре «источник, сырое имя»: `change:visible` — триггер и
  у `visible`, и у `present`, а потребитель обязан получить одно событие. Для
  состояния повтор, наоборот, обязателен: каждое свойство пересчитывается на
  свой триггер.
- Событие привязки (`update:<проп>`) уходит после события ядра, с новым
  значением, и только на изменение — не при монтировании.
- `bundle:create` и `plugin:event` — обычные события корневого дескриптора.
- Все подписки снимаются при размонтировании.

**Несъеденные пропсы.** React, Solid и Svelte отдают остаток пропсов в корневой
узел атрибутами. «Съедено»: пропсы (под обоими именами), имена событий и
триггеров, слоты (с заменой `default` на `children`), `ctrl`, `embedded`. Без
слотов в списке `leading={<Icon/>}` доехал бы до DOM атрибутом.

### 6.3 Плагины и расширения снаружи

Своё поведение компоненту добавляют без правки библиотеки, тремя путями:

```ts
// 1. Одному компоненту
<Button @bundle:create="(b) => b.use(TTimerPlugin)" />
<ListBox @engine:create="(e) => e.use(new TProbeExtension())" />

// 2. Всем компонентам типа — в точке входа приложения
usePlugins(TButton, [TTimerPlugin])

// 3. Тема
useTheme(oren)
```

**Реестр на тип.**

- Тип — **класс ядра**, соответствие — `instanceof`: подходит и наследник,
  переданный через `ctrl`.
- `scope`: `'own'` (по умолчанию) — только компоненты, которые поставил
  пользователь; `'all'` — и детали чужой разметки (у компонента задан
  `embedded`). У темы умолчание — `'all'`.
- Плагины реестра ставятся после плагинов дескриптора, в порядке регистрации,
  до `bundle:create`. Один класс — один экземпляр, с опциями последней
  регистрации.
- Внешний плагин только добавляет: класс, уже входящий в состав компонента, —
  ошибка сборки.
- Компоненту без своих плагинов реестр набора не создаёт.
- Регистрация возвращает отмену и действует на компоненты, собранные после
  неё; уже собранных не касаются ни она, ни отмена.
- Правило выбора («тип + scope + embedded») одно на реестр плагинов и реестр
  расширений коллекций.

**Пропсы и события внешнего плагина.** Поверхность компонента объявляет только
дескриптор, и она одна на тип во всех шести адаптерах. Внешний плагин в неё не
попадает: статический слой объявляет поверхность раньше регистрации, а
поставить плагин можно и после монтирования. Поэтому на все внешние плагины у
компонента один проп и одно событие:

```ts
// Контракт — один раз, рядом с классом
definePlugin({
	ctor: TTimerPlugin,
	namespace: 'timer',
	contribution: { props: { ms: { type: Number, triggers: ['change:ms'] } }, events: ['tick'] },
})
usePlugins(TButton, [TTimerPlugin])

<Button :plugin-props="{ timer_ms: 500 }" @plugin:event="({ name, args }) => …" />  // Vue
<Button pluginProps={{ timer_ms: 500 }} onPluginEvent={({ name, args }) => …} />   // React, Solid, Svelte
<soldy-button [pluginProps]="{ timer_ms: 500 }" (pluginEvent)="…" />                // Angular
el.pluginProps = { timer_ms: 500 }; el.addEventListener('plugin:event', …)         // Web Components
```

- Ключи `pluginProps` — имена пропсов в общем формате (`timer_ms`).
- **Путь один, когда бы плагин ни встал**: при сборке (реестр) или позже
  (`bundle.use`, например в `bundle:create`). О появлении и уходе плагина
  сообщает набор (`use`, `remove`). Значения, пришедшие раньше плагина, ждут
  его.
- Правила записи — те же, что у пропсов компонента.
- События плагина — явные и триггеры его пропсов, без повторов — уходят
  конвертом `{ name: 'timer:tick', args }` на **шину инстанса**: его видят и
  адаптер, и тот, у кого на руках только `ctrl`.
- Плагин без объявленного контракта работает, но значений из `pluginProps` не
  получает и событий наружу не шлёт. Плагин дескриптора через `pluginProps` не
  пишется: его пропсы уже в поверхности.
- Типы ключей приложение дописывает расширением интерфейса
  `IExternalPluginProps` модуля `@soldy/setup`.

**Расширения коллекций.** `useExtensions(КлассВладельца, [(owner) =>
extension], { scope? })`. Регистрируется фабрика, а не экземпляр. Ставит
расширения общий слой в момент привязки движка к компоненту; движок и ядро о
реестре не знают. Владелец — **компонент** (хозяин набора), а не фасад. Имя,
занятое расширением другого класса, — ошибка; то же расширение в том же движке
(движок передан двум компонентам) второй раз не ставится.

### 6.4 Расширения контекста для коллекций

Проводка коллекций одинакова во всех фреймворках и живёт в общем слое.
Расширение читает и связывает **значения**; оно не читает DOM-узел и не решает,
что с ним делать (`el.closest`, `querySelector` — это плагин).

Значения от родителя к детям передаёт **лифт** — абстракция над механизмом
фреймворка (`provide`/`inject`, React Context, DI Angular): по типизированному
ключу получают объект с `down(value)` и `up()`. Общий слой определяет ключи,
типы значений и базовый класс лифта; фабрику по ключу даёт адаптер и передаёт
расширению опцией `elevator`. Ключей три: движок коллекции для детей, функция
регистрации элемента у владельца, признак drag-контекста.

| Расширение (имя и опции заморожены)                    | Подключается к             | Обязанности                                                                                                                                                                                                                             |
| ------------------------------------------------------ | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TCollectionExtension` `{ elevator }`                  | контексту фасада владельца | Требует у инстанса `engine`, иначе ошибка. Опускает движок детям. Привязывает движок к `TCollectionBundlesPlugin` набора. Ставит в движок расширения реестра (6.3). Опускает функцию регистрации элемента.                              |
| `TCollectionItemExtension` `{ item, elevator }`        | контексту фасада элемента  | Берёт движок у лифта и отдаёт фасаду контекст элемента (`setContext`). Регистрирует элемент у владельца, снятие регистрации — на `destroy`. Кладёт в `meta` движка входные пропсы фасада элемента, заданные разметкой, по сырым именам. |
| `TDragAndDropExtension` `{ elevator }`                 | контексту контейнера       | Опускает признак drag-контекста.                                                                                                                                                                                                        |
| `TDragAndDropCollectionExtension` `{ elevator }`       | контексту фасада владельца | Если выше есть drag-контекст — активирует `TDragPlugin` набора на движке.                                                                                                                                                               |
| `TTabsContentBindingExtension` `{ content, elevator }` | контексту фасада панели    | Находит таб с тем же `value`, отдаёт фасаду его контекст, пишет панели её сторону ARIA-связки; перерешает, когда появился таб (`item:added`) или сменилось `value`; при уничтожении снимает ровно то, что поставило.                    |

**Кто создал элемент, тот им владеет.** Элемент, пришедший из данных (`items`),
уже лежит в коллекции: его монтирование и размонтирование состав не меняют.
Элемент, объявленный в разметке, добавляется в конец при монтировании (порядок
DOM) и удаляется при размонтировании. Набор плагинов элемента, если он есть,
регистрируется у владельца.

Совместимость расширения с компонентом проверяется **при компиляции**:
расширение, которому нужен инстанс с `engine`, нельзя подключить к контексту
компонента, у которого `engine` нет.

## 7. Требуется: типы

Цель: автор дескриптора, автор компонента адаптера и автор приложения **не
пишут ни одного аргумента типа**. Дескриптор — единственный источник типов;
адаптеры не импортируют интерфейсы пропсов и карты событий из ядра.

Из фабрики дескриптора (`typeof ButtonDescriptor`) выводятся:

- **пропсы компонента** — интерфейс пропсов его класса ядра (без своего класса
  — родительского), плюс входы плагинов под именами с неймспейсом
  (`aria_label?: string`);
- **события** — карта событий класса, **суженная до опубликованных имён**:
  `events` и триггеры пропсов, свои и унаследованные. Событие, которое класс
  шлёт, но дескриптор не публикует (`change:present`), в типы не входит: тип,
  обещающий колбэк, который адаптер не вызовет, — ошибка. Плюс события плагинов
  с неймспейсом (`element:ready`), без внутренних событий базы плагина;
- **выходы плагинов** — защищённые пропсы плагинов (`layout_styles`,
  `dismiss_ownerAttribute`) с типами геттеров плагина; их читает разметка;
- **слоты** — имя → scope; слот без scope — пустой объектный тип (`object`, не
  `Record<string, never>`: адаптеры отличают его по `keyof`);
- **инстанс**.

Вывод у плагина: состав — из объявления (незащищённые — входы, защищённые —
выходы), тип значения — у одноимённого свойства класса плагина или у `get`
декларации, события — карта класса, суженная до объявленных, тип опций `.with`
— второй параметр `install`. Второй записи тех же типов рядом с объявлением
нет.

Проверки при компиляции:

- имя в `events` и в `triggers` дескриптора с классом ядра обязано быть ключом
  карты событий этого класса; опечатка — ошибка. У дескриптора без класса
  (корень, база коллекций) сверять не с чем — имена копятся, карту к ним
  прикладывает наследник, и ни одно имя при этом не должно потеряться;
- значение scope слота без типа (`String` вместо `defineType<string>(String)`)
  не компилируется;
- неверные опции в `.with()` не компилируются;
- `ctrl` чужого компонента не компилируется.

**Тип инстанса контекста.** Адаптеры объявляют проп `ctrl` **интерфейсом** ядра
(`IButton`), а дескриптор знает **класс** (`TButton`). Контекст обязан обещать
интерфейс: под `ctrl` приходит любая его реализация, не обязательно класс
библиотеки. Без `ctrl` в опциях тип инстанса — класс дескриптора.

Тип состояния, которое адаптер отдаёт разметке: свойства инстанса так, как их
видит разметка (у объекта со своим `valueOf()` — тип снимка, примитивы не
расширяются, все ключи необязательны), плюс выходы плагинов того же вида.
Граница между рантаймом («словарь по именам») и этим типом — **одна на все
адаптеры** и в одном месте.

Требование к форме типов: **новый факт о компоненте в типах не должен менять
сигнатуры** функций, через которые проходят дескриптор и контекст. Позиционные
списки фантомных параметров, которые каждая функция протаскивает дальше, —
именно тот дефект, из-за которого слой переписывается.

## 8. Сценарии приёмки

Каждый сценарий — требование. Сформулированы без привязки к API: как именно их
проверить, решает исполнитель, но проверка обязана существовать.

**Описание**

1. Фабрика дескриптора, вызванная дважды, отдаёт один и тот же объект.
2. У Frame умолчание `visible` — `false`, хотя родитель объявил `true`;
   декларация родителя при этом не изменилась.
3. У дескриптора с классом без `defaultValues` поля умолчания у пропа нет
   вовсе; у класса с `closable: undefined` ключ есть, значение `undefined`.
4. Опция `.with({ flip: false })` становится умолчанием пропа плагина;
   `.with({ flip: undefined })` — нет, остаётся умолчание класса.
5. `.with()` не меняет ни исходное определение, ни контракт класса, по которому
   подключается тот же плагин, поставленный снаружи к другому компоненту.
6. Наследник с плагином того же класса получает один плагин на месте
   родительского; со слотом того же имени — один слот на месте родительского.
7. Попытка изменить список деклараций дескриптора ничего не меняет.
8. Два объявления с одним полным именем — ошибка при сборке компонента.

**Сборка**

9. Свой инстанс: пропсы приходят в конструктор, сеттеры при сборке не
   вызываются.
10. Внешний `ctrl` с `text = 'A'`, разметка передала `text: 'B'` — после сборки
    `'B'`. Разметка передала значение, равное умолчанию, — остаётся `'A'`.
11. Проп плагина из пропсов сборки (`aria_label`) доходит до плагина; равный
    умолчанию — не пишется.
12. `bundle:create` приходит подписчику, который подписался сразу после
    создания контекста; следом плагины получают `created()`.
13. Контекст уничтожен до микрозадачи — ни `bundle:create`, ни `created()`.
14. Плагин, поставленный обработчиком `bundle:create`, объявляется вместе с
    остальными.
15. У компонента без плагинов набора нет, и регистрация приложения его не
    создаёт.
16. Два контекста на одном наборе: уничтожение второго набор не трогает;
    уничтожение первого отвязывает узел, затем уничтожает набор.
17. `embedded` берётся из опций, а без них — из пропсов сборки.

**Состояние**

18. Подписчик сразу получает значение каждого свойства с триггерами.
19. Инстанс изменился между созданием контекста и подпиской — подписчик
    получает новое значение.
20. `present` пересчитывается и на `change:rendered`, и на `change:visible`.
21. Снимок — тот же объект, пока значения не менялись; после изменения —
    новый. `classes` с тем же содержимым нового снимка не даёт.
22. После отписки последнего подписчика на шине инстанса не остаётся
    обработчиков слоя; это же верно после размонтирования при внешнем `ctrl`.
23. Плагин заменил объект `styles` — состояние получило новое значение.

**Входы**

24. Полный набор пришёл повторно с теми же значениями — в ядро ничего не
    пишется, даже если ядро с тех пор изменило проп.
25. `open={false}` в разметке, список открыт кликом, сменился `placeholder` —
    список остаётся открытым.
26. Заданный `text` сняли (`undefined`) — `text` равен умолчанию `''`.
27. Снятый `closable` элемента Tabs становится `undefined` («как у владельца»),
    а не остаётся `true`.
28. Проп, который ни разу не задавали, приходит `undefined` — у внешнего `ctrl`
    ничего не меняется.
29. Проп, заданный при сборке, тоже «задан»: снятый, он сбрасывается.
30. После сброса проп снова «не задан»: повторное снятие ничего не пишет.
31. У пропа без объявленного умолчания (`items`) снятие значение не меняет.
32. Снятый проп сбрасывается к умолчанию, даже если ядро с тех пор его меняло.
33. Дельта `{ text: 'B' }` пишет только `text`; остальные заданные пропсы не
    сбрасываются.
34. Значение, которое уже лежит в ядре, сеттер не получает.
35. Снятое `aria_label` убирает `aria-label`; снятые `width` и `height` иконки
    уходят из её стилей; снятый якорь отвязывает панель Frame.

**События**

36. Одно изменение `visible` — одно событие `change:visible` наружу.
37. Событие плагина приходит под именем с неймспейсом (`element:ready`,
    `onElementReady`, `elementReady`).
38. Событие привязки Vue приходит после события ядра, с новым значением, и не
    приходит при монтировании.
39. После отписки событий обработчиков на шинах инстанса и плагинов не
    остаётся.

**Плагины снаружи**

40. Регистрация на `TButton` действует на кнопку, собранную после неё, и не
    действует на собранную до; после отмены — не действует на новые.
41. Кнопка с `embedded` получает только регистрации со `scope: 'all'`.
42. Подкласс, переданный через `ctrl`, получает регистрацию базового класса.
43. Повторная регистрация того же класса — один экземпляр, опции последней.
44. Регистрация класса из состава компонента — ошибка с именами плагина и
    компонента.
45. `pluginProps: { timer_ms: 500 }` при сборке доходит до плагина реестра;
    значение, равное умолчанию, — нет.
46. Значение в `pluginProps` пришло раньше, чем плагин поставлен через
    `bundle.use`, — плагин получает его при установке.
47. Ключ пропал из `pluginProps` — проп плагина вернулся к умолчанию.
48. Событие внешнего плагина приходит конвертом `{ name: 'timer:tick', args }`
    и адаптеру, и подписчику `ctrl.events.on('plugin:event')`; триггер,
    объявленный и событием, и триггером пропа, — один раз.
49. После `bundle.remove` значения и события плагина больше не ведутся.
50. Поверхность компонента от регистраций не зависит: пропа `timer_ms` в ней
    нет, `pluginProps` и `plugin:event` — есть.

**Коллекции**

51. Расширение владельца опускает движок и регистрацию; элемент из разметки
    добавляется в конец, при размонтировании удаляется.
52. Элемент, уже лежащий в `items`, при размонтировании из коллекции не
    удаляется.
53. Расширение реестра ставится в движок один раз, даже если движок передан
    двум компонентам; занятое имя с другим классом — ошибка.
54. Панель Tabs, смонтированная раньше своего таба, связывается с ним, когда
    таб появился; при смене `value` — перевязывается; при уничтожении снимает
    только свои ARIA-атрибуты.
55. Входные пропсы фасада элемента, заданные разметкой (`active`), попадают в
    `meta` движка.

**Типы** (проверяются компилятором: `expectTypeOf`, `@ts-expect-error`)

56. `change:text` у Button есть в типах событий; `change:present` — нет.
57. Имя события, объявленное у корня без класса (`bundle:create`), есть в типах
    Button; ни у одного экспортируемого дескриптора сужение не теряет имён.
58. `aria_label` есть в пропсах Button; `layout_styles` есть в выходах Frame и
    отсутствует у Button; `keyboard:escape` у Select отсутствует (плагин шлёт
    его только внутри набора).
59. Триггер с опечаткой, scope без `defineType`, неверные опции `.with()`,
    расширение коллекции на компоненте без `engine` — не компилируются.
60. У `LIST_PROPS`, подмешанных спредом, имена триггеров дошли до типов событий
    ListBox и Select.

**Сторожа содержимого дескрипторов** (дескрипторы остаются — сторожа обязаны
вернуться)

61. По каждому экспортируемому дескриптору ключи выведенного типа пропсов
    совпадают с незащищённым рантайм-составом в обе стороны; то же для выходов
    плагинов. Коллекционная часть сверяется в строке владельца.
62. У незащищённого пропа с `Boolean` в типе умолчание объявлено и равно
    стартовому значению свежего инстанса или плагина: Vue приводит такие пропсы
    сам.
63. У каждого незащищённого пропа с триггерами объявлен ключ умолчания;
    исключения — `items` и `mode` у наследников базового класса коллекций.
64. Тип пропа — конструктор рантайма или их массив, а не обёртка `defineType`.
65. Рантайм-функции имён и их типы-зеркала дают одинаковый результат.
66. `npm run generate --workspace=@soldy/ui-angular` не меняет ни одного файла.

## 9. Нефункциональные требования

- **Никаких костылей** (`AGENTS.md`, одноимённый раздел). Отдельно для этого
  слоя, потому что именно эти дефекты привели к переписыванию:
  - режим или флаг внутри общего метода ради частного случая — нет; иначе
    ведёт себя — отдельная сущность;
  - один факт — одна запись. Параллельные структуры об одном и том же пропе,
    склеиваемые по строковому ключу, копии умолчания, второй путь к тем же
    данным — нет;
  - одно правило — одно место. «То же значение не пишем», «снятый проп — к
    умолчанию», «повтор события не пробрасываем» не дублируются;
  - функции-мешки и россыпь свободных функций вокруг анемичных данных — нет.
    Ожидается объектная модель с явными ролями; выбор приёмов проектирования —
    за исполнителем, с обоснованием.
- **Приведения типов запрещены** линтером (`soldy/no-casts`): `as never`,
  `as unknown as X`, `<T>x`, `x!`, `@ts-ignore`. Граница «рантайм-словарь →
  тип состояния» — единственное место с обычным `as`, одно на все адаптеры.
  `any` допустим только там, где это описано в `AGENTS.md` («`any`: где он
  честный»).
- Кэшируется только то, что зависит от типа, а не от монтирования; ключи кэша
  — объекты (дескриптор), а не строки.
- Побочные эффекты при импорте модуля — минимальны и осознанны: сейчас сборщик
  не может отбросить неиспользуемые плагины. Желательно, чтобы приложение с
  одной кнопкой не тянуло плагины Select.
- Соглашения репозитория: префиксы `T` (классы, типы) и `I` (интерфейсы);
  классы в файлах `*.class.ts`; у каждого файла шапка, первая строка которой —
  одно предложение о файле; комментарии по-русски и объясняют «почему»; файл с
  рантаймом типов не экспортирует; внутри пакета он сам себя по имени не
  импортирует.
- Тесты — vitest; проверки типов — в тех же файлах, их ловит шаг CI «Типы».
- Любая правка библиотечного пакета несёт changeset (`AGENTS.md`, «Версии
  пакетов»); изменение ломающее — уровень `minor`.

## 10. Состав работы

1. **Проектная записка** до кода: сущности и их обязанности, границы модулей и
   направление зависимостей между ними, публичный API для адаптерного слоя,
   способ вывода типов, какие приёмы проектирования выбраны и почему,
   один пакет или два. Записку утверждает владелец.
2. Реализация общего слоя с тестами по сценариям раздела 8.
3. Перевод адаптерного слоя шести фреймворков на новый API без правок
   компонентов; перевод адаптерного файла стенда и пакета темы.
4. Проверки: тесты всех пакетов, типы всех пакетов и стенда (команды — в
   `AGENTS.md`, раздел «Commands», и в `.github/workflows/ci.yml`), eslint,
   отсутствие дрейфа метаданных Angular.
5. Документация: разделы `AGENTS.md` и `docs/architecture.md` о слое
   переписываются под новую реализацию; сторож структуры слоя создаётся заново
   под новые границы модулей.

Известное состояние на входе: в `packages/ui/vue` падает один тест, не
связанный со слоем, — `template-root.spec.ts > popover/Popover.vue`.

## Приложение А. Тесты `packages/setup/__tests__`

**Остаются без правок** — от API слоя не зависят (интеграционные тесты ядра и
плагинов и сторожа репозитория): `overlay`, `select-backspace`,
`select-editable`, `select-keyboard`, `select-pointer`, `list-height`,
`list-keyboard`, `tabs-layout`, `driver-access`, `embedded-markup`,
`framework-mechanisms-components`, `theme-values-markup`,
`workspace-manifests`. Им нужен `helpers.ts`: в нём остаются
`createPluginContext`, `required` и заглушки `ResizeObserver`.

**Остаются как приёмка поведения**, зовут только замороженный вход; правятся
лишь пути импорта: `aria-plugin` (`createAdapterContext`), `plugin-registry`
(`createAdapterContext`, `usePlugins`), `icons` (реестр иконок).

**Удаляются вместе со слоем** — проверяли прежнее внутреннее устройство;
поведение перенесено в раздел 8: `base`, `binding`, `adapter`, `descriptors`,
`descriptor-events`, `descriptor-props-types`, `plugin-events`, `slots`,
`prop-defaults`, `registered-plugin-contract`, `plugins-access`,
`extension-registry`, `facade-props`, `value-identity`, `setup-structure`.

Тесты адаптеров (`packages/ui/*/__tests__`) — приёмка. Те из них, что зовут
удалённый API слоя напрямую, переписываются с сохранением сценария и ожиданий.

## Приложение Б. Замороженные имена `@soldy/setup`

Описание: `defineDescriptor`, `defineComponent`, `definePlugin` (+ `.with`),
`defineType`, `IComponentPropDefinition`, все `*Descriptor` и
`*PluginDescriptor`.

Монтирование: `createAdapterContext` с опциями `ctrl`, `props`, `options`,
`embedded` и конфигом `bundle`; у контекста — `instance`, `bundle`, `embedded`,
`use`, `get`, `bindElement`, `destroy`, `events` с событием `destroy`.

Расширения контекста: `TCollectionExtension`, `TCollectionItemExtension`,
`TDragAndDropExtension`, `TDragAndDropCollectionExtension`,
`TTabsContentBindingExtension` — с опциями из раздела 6.4.

Приложение: `usePlugins`, `useExtensions`, `defineTheme`, `useTheme`,
`ITheme`, `IThemePlugins`, `IThemeExtensions`, `IExternalPluginProps`,
`setIcons`, `getIcon`, `hasIcon`, `resetIcons`, `missingIconRoles`,
`ICON_ROLES`, `MISSING_ICON`, `TIconSource`, `TIconRole`, `TIconPack`.

Прочее: `withParts`; проп `pluginProps`, события `bundle:create` и
`plugin:event`; формат имени пропа плагина `неймспейс_имя`.

Всё, чем общий слой обменивается с адаптерным слоем (стратегия имён,
поверхность для статики, подписка на состояние, запись входов, проброс
событий, типы для пропсов и состояния), — **не заморожено**: это предмет
проектирования.
