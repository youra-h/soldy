## 2. Идея в трёх тезисах

**1. Вся изменяемая память слоя — ячейки.** Ячейка (`TCell`) — значение, правило
«то же самое» и подписчики; контракт как у стора Svelte и атома nanostores:
`subscribe` сразу отдаёт значение, `listen` — только изменения. Правила ТЗ при
этом перестают быть кодом и становятся свойством примитива:

- «снимок — тот же объект, пока ничего не сменилось» — ячейка не будит
  подписчиков на том же значении, значит снимок никто не сбрасывает;
- «повтор полного набора ничего не пишет» — ячейка входа не сменилась;
- «ни разу не задавали / задали и сняли / после сброса снова не задан» — это
  просто переходы значения ячейки `undefined → x → undefined`, без флага
  «задан»;
- «значения `pluginProps` ждут плагин» — мешок лежит в ячейке, пришедший плагин
  читает её текущее значение.

**2. Срез вертикальный, по свойству, а не по фазе.** Линия (`TLine`) — описание
пропа + владелец + имя во фреймворке. Это единственный объект, который знает
про свойство всё, поэтому `write` / `reset` / `accept` / `seed` живут в нём по
одному разу — и для сборки, и для обмена, и для внешних плагинов. Прошлый
рефакторинг пришёл к тому же (`TProperty`) — значит, направление верное;
разница в том, что линия несёт и имя во фреймворке, и сшивка «поверхность ×
аксессор по строке» исчезает.

**3. Все, кто владеет свойствами, — участники одного вида.** Участник
(`TMember`) — владелец и его контракт. Инстанс, плагин дескриптора, внешний
плагин и **сама связка** (владелец `pluginProps`) — одно и то же для обмена.
Следствия:

- `pluginProps` — не «особый приёмник»: у `TExternalPlugins` есть обычный
  сеттер `pluginProps`, и обычная линия пишет в него обычным правилом;
- внешний плагин обслуживает **тот же** `TExchange`, что и компонент, — с общим
  профилем имён, мешком вместо пропсов фреймворка и конвертом вместо `emit`.
  Второй реализации правил нет, «правила те же» выполняется тем, что код один;
- «плагина в чужом наборе нет» = нет участника. Ни одной проверки дальше.

## 4. Ключевой код

Целиком — в `packages/setup/adapter/exchange/`. Здесь — места, где видно, куда делись правила.

Линия: четыре правила записи, каждое — одна строка.

```ts
write(value: unknown): void {
	if (!this.writable || sameValue(this.read(), value)) return   // protected; то же значение

	this.spec.assign(this.owner, value)
}

reset(): void {
	if (this.spec.hasDefault) this.write(this.spec.default)       // значим ключ, а не значение
}

accept(value: unknown): void {                                    // от фреймворка: undefined = «сняли»
	if (value === undefined) this.reset()
	else this.write(value)
}

seed(value: unknown): void {                                      // начальное значение
	if (value === undefined) return
	if (this.spec.hasDefault && sameValue(value, this.spec.default)) return

	this.write(value)
}
```

Вход: вся «память того, что задал фреймворк» — конструктор и два метода.

```ts
constructor(readonly line: TLine, given: unknown) {
	this._cell = new TCell(given)                          // память начинается с пропсов сборки
	this._cell.listen((value) => line.accept(value))       // сменил фреймворк → линия решает, что делать
}

offer(value: unknown): void {                              // полный набор, одиночный проп
	this._cell.set(value)
}

push(value: unknown): void {                               // дельта: наличие ключа — уже изменение
	if (!this._cell.set(value) && value !== undefined) this.line.accept(value)
}
```

Три способа доставки отличаются только тем, **что считать изменением**; что с
изменением делать — решает линия.

Внешний плагин: ни одного собственного правила.

```ts
private readonly _onUse: TPluginBundleEvents['use'] = (ctor, plugin) => {
	const contract = this._contractOf(ctor)

	if (!contract) return

	const member = new TMember(plugin, contract.props, contract.events, contract.namespace)
	const exchange = new TExchange([member], CommonProfile, this._bag.value)   // мешок = «пропсы сборки»

	exchange.seed(member)

	const offBag = this._bag.listen((bag) => exchange.inputs.full(bag))        // мешок = «полный набор»
	const offEvents = exchange.events.listen((name, args) => this._announce({ name, args }))
	…
}
```

«Ключ пропал из мешка — проп вернулся к умолчанию» здесь нигде не написано: это
обычное поведение полного набора.

## 5. Сборка (в прототип не вошла)

Шесть шагов раздела 6.1 читаются в одном месте сверху вниз — как в ТЗ:

```ts
export function createAdapterContext(descriptor, options, config = {}) {
  const origin = TInstanceOrigin.of(descriptor, options) // 1. ctrl или конструктор
  const tenancy = TBundleTenancy.of(descriptor, origin, options, config)
  //    └ TOwnBundle: состав = дескриптор + реестр (2), набор (3), объявление на микрозадаче (4),
  //      TExternalPlugins, отвязка узла и destroy
  //    └ TSharedBundle: участники — плагины дескриптора, найденные в чужом наборе (6); всё остальное пусто
  //    └ TNoBundle: bundle = null
  const members = [origin.member, ...tenancy.members]
  const context = new TAdapterContext(descriptor, origin, tenancy, members, options.props ?? {})

  if (origin.external) context.seed(origin.member) // 5. свой инстанс получил пропсы конструктором
  tenancy.seed(context) //    свой набор — пишет, чужой — пусто

  return context
}
```

Две вещи стоит отметить.

- **Линии не зависят от профиля.** Имя пропа одно во всех фреймворках, поэтому
  линии, порт входов и стор состояния строятся при сборке, а профиль нужен
  только пробросу событий (имена событий, привязка) и списку «съеденного».
  Начальные значения поэтому пишет та же линия, что потом ведёт обмен, — а не
  отдельный шаг со своим чтением пропсов.
- **`TExternalPlugins` подписывается на набор после плагинов дескриптора и до
  плагинов реестра.** Реестр ставит свои плагины обычным `bundle.use` — и они
  приходят тем же событием `use`, что и плагин из обработчика `bundle:create`.
  «Путь один» обеспечен порядком трёх строк, а не проверкой.

Описание типа: порядок «заменяет, оставаясь на месте» (слоты, плагины) даёт
обычный `Map` — `set` по существующему ключу позицию не меняет. Умолчания
наследник пересчитывает от итогового класса: `spec.rebase(ctor.defaultValues)`
возвращает новое замороженное описание, родительское не трогается.

## 6. Адаптеры

Форма API продиктована фреймворками (`useSyncExternalStore` хочет
`subscribe` + `getSnapshot`, остальные — значение по имени), поэтому внешне она
близка к прежней. Проверка концепции — в том, что адаптеру нечего решать.

```ts
// Vue
const link = adapter.connect(VueProfile)
const refs: Record<string, ShallowRef<unknown>> = {}

const offs = [
	link.state.subscribe((name, value) => {
		;(refs[name] ??= shallowRef()).value = value                      // куда положить
	}),
	...[...link.inputs].map((input) =>
		watch(() => link.inputs.pick(props, input), (value) => input.offer(value)),
	),
	link.events.listen((name, args) => emit(name, ...args)),             // как отдать
]

// React
const state = useSyncExternalStore(link.state.subscribe, link.state.getSnapshot)
useEffect(() => link.inputs.full(props))
useLayoutEffect(() => link.events.listen((name, args) => call(propsRef.current, name, args)), [link])

// Angular / Web Components
syncInputs(changes) { link.inputs.delta(changes) }
```

## 7. Типы и пакеты

**Типы — без изменений по сравнению с последним рефакторингом, и это
сознательно.** Один параметр типа у `defineComponent` (сами опции, литералом),
контракт-мешок `IComponentContract` как единственный параметр дескриптора,
контекста и `useAdapter` — это и есть требование раздела 7 («новый факт не
меняет сигнатур»). Рантайм-концепция от типов не зависит: `TPropSpec`, `TLine`,
`TCell` работают со словарями по именам, а граница «словарь → тип состояния»
остаётся одной функцией с единственным `as`. В прототипе типы вывода не
проверялись.

**Один пакет.** У `@soldy/accessor` был один потребитель — `@soldy/setup`, а
граница между ними резала правила пополам (запись — там, память — тут). Ядро
обмена остаётся изолированным, но модулем, а не пакетом:

```
setup/
  define/       описание типа: TDescriptor, TPropSpec, TPluginSpec, типы вывода
  naming/       стратегии имён и типы-зеркала                       (как есть)
  surface/      TSurface: дескриптор × профиль
  exchange/     TCell, TLine, TMember, порты, TExchange             ← прототип; знает только TPropSpec и профиль
  mount/        createAdapterContext, TAdapterContext, владение набором, TExternalPlugins
  registry/     usePlugins, useExtensions, тема, иконки
  extensions/   коллекции и лифт                                    (как есть)
  descriptors/  заморожено
```

Зависимости: `descriptors → define`; `surface → define, naming`;
`exchange → define, naming`; `mount → exchange, surface, registry`;
`extensions → mount`. Сторож структуры проверяет именно эти стрелки.

## 8. Правило ТЗ → одно место

| Правило                                                            | Где                                                      |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| То же значение не пишется; `protected` не пишется                  | `TLine.write`                                            |
| Снятый проп — к умолчанию; значим ключ                             | `TLine.reset`, `TPropSpec.hasDefault`                    |
| `undefined` = «сняли»                                              | `TLine.accept`                                           |
| Начальное: `undefined` и равное умолчанию ничего не задают         | `TLine.seed`                                             |
| Пишется только то, что сменил фреймворк; память с пропсов сборки   | `TInput` (ячейка)                                        |
| В дельте наличие ключа — изменение                                 | `TInput.push`                                            |
| Снимок через `valueOf()`                                           | `snapshotOf` ← `TPropSpec.read`                          |
| «Сменилось ли»: простое — по содержимому, прочее — по идентичности | `sameValue` — равенство ячейки выхода и сверка в `write` |
| Сначала подписка, потом чтение; шина — пока есть подписчик         | `TStateStore.subscribe`                                  |
| Событие без повторов по «источник, имя»                            | `TMember.published` → маршруты `TEventRelay`             |
| Событие привязки — после события ядра, не при монтировании         | обработчик маршрута `TEventRelay`                        |
| Шина — `events`, иначе сам объект, иначе источника нет             | `busOf`                                                  |

## 9. Открытые вопросы

1. **Кто владеет `ctrl`, `embedded`, `pluginProps`.** В концепции это пропсы
   участника-связки, а не инстанса. Но дескриптор заморожен, и по нему не видно,
   что эти три пропа — особые (у `CollectionDescriptor` тоже нет класса, а его
   пропсы принадлежат фасаду). Варианты: (а) `entity.descriptor.ts` переезжает
   в `mount/` — это контракт связки, а не компонента, — и участник узнаётся по
   идентичности описаний; (б) явная таблица из трёх имён в `mount/`. Я за (а):
   содержимое файла не меняется, меняется только его место.
2. **Умолчание `pluginProps`.** Чтобы снятый проп сбросил плагины, ему нужно
   объявленное умолчание `{}`. У Entity класса нет — умолчание естественно
   объявить `static defaultValues` у класса-владельца (`TExternalPlugins`).
3. **Сверка при записи — поверхностная** (`sameValue`). Новый массив `items` с
   тем же содержимым на каждом рендере React в ядро не пишется. Кажется верным
   (сеттер `items` пересоздаёт элементы), но это решение, а не следствие ТЗ.
4. **`write` читает свойство перед записью.** Для вычисляемых геттеров со
   снимком это лишнее чтение на каждую запись. Записываемые пропсы обычно
   простые; если найдётся дорогой — лечится у него, а не в линии.
5. **ТЗ воспроизводит прежнюю раскладку.** Если слой будет писать другая
   модель, стоит приложить эту записку как утверждённую проектную (п. 10.1 ТЗ)
   — иначе она придёт туда же, куда пришёл я в первом наброске.

## 11. Как скрещивать с прежним кодом

Из прежнего берётся без изменений по смыслу: типы вывода и контракт-мешок,
дескрипторы, `naming/`, расширения коллекций и лифт, реестры, иконки,
`TOwnPlugins` / `TSharedPlugins` как идея.

Заменяется: `@soldy/accessor` целиком, связка с тремя объектами по
направлениям, приёмник `pluginProps`, второй проброс событий у внешних
плагинов, шаг `applyInitialProps` — всё это становится `exchange/` из
прототипа плюс участник-связка.

## 12. Состояние после объединения (2026-09-20)

Объединение сделано в ветке `refactor/setup2`. Разделы 1–11 — замысел до него;
здесь — что получилось. Актуальное описание слоя — `AGENTS.md`, «Структура
`packages/setup`», и `docs/architecture.md`, Layers 2, 5 и 5b.

**Взято из `refactor/setup`:** `define/` (один параметр типа, контракт-мешок,
`TComponentDescriptor`, `TPluginDefinition.with`), `registry/`,
`adapter/common/`, идея «свой / чужой набор», объявление набора на микрозадаче.

**Из прототипа:** `adapter/exchange/` целиком, `TExternalPlugins` поверх
`TExchange`, связка как участник.

**Решено по ходу:**

- Анемичная `IPropDeclaration` стала классом `TPropSpec` с той же формой полей
  — стенд и кодоген Angular её читают как раньше (`Object.hasOwn(spec,
'default')` работает: поле объявлено через `declare` и появляется, только
  если умолчание есть).
- Поверхность находит запись по **объекту имени** (`TName`), а не по описанию
  и не по строке: имя создаётся один раз на объявление и переживает `rebase`,
  поэтому описание наследника и описание `pluginProps` с умолчанием владельца
  находят ту же запись.
- Открытый вопрос 1 закрыт вариантом (б): таблица из трёх имён в
  `create-adapter-context.ts` — это имена опций самой функции. `ctrl` и
  `embedded` линий не получают вовсе, `pluginProps` принимает связка.
  `entity.descriptor.ts` остался на месте.
- Открытый вопрос 2 закрыт: `static defaultValues = { pluginProps: {} }` у
  `TExternalPlugins`.
- Дельта-команда (`TInput.push`) — не новое поведение: прежний `writeChanged`
  делал то же самое.
- Снимок состояния читается при первом обращении и дальше меняется только
  триггерами и подпиской — так требовал прежний тест для рендера React.
- Набор «никакой» не стал третьим классом: `TSharedBundle` — «набор не наш:
  чужой или никакого», все его шаги пусты в обоих случаях.

**Проверки:** прежние тесты связки (45), внешних плагинов (16), доступа к
набору (11), контекста (17), дескрипторов и умолчаний перенесены на новый API
механически, без правки ожиданий, — 775 тестов `@soldy/setup` зелёные. Типы
всех пакетов по списку CI, `ngc`, `svelte-check`, eslint репозитория — чисто.
Кодогенерация Angular не изменила ни одного файла. Во Vue падает один тест,
названный в ТЗ заранее (`template-root › Popover.vue`).

**Размер.** По коду без комментариев и на том же наборе модулей (описание,
реестры, сборка, поверхность, обмен, общие функции): было 1 778 строк в двух
пакетах, стало 1 639 в одном; ядро обмена — 318. Выигрыш не в объёме, а в том,
что правила записи, память и проброс событий перестали существовать в двух
экземплярах.

**Tree-shaking (включено у setup 2026-09-20; у core — нет).** `usePlugins` принимает определение плагина, сторож — `__tests__/tree-shaking.spec.ts`. Бандл с одним `ButtonDescriptor`:
466 KiB как есть, 159 KiB с `"sideEffects": false` у `@soldy/setup`, 77 KiB —
если то же у `@soldy/core`. Причина не в слое, а в вызовах `defineDescriptor` /
`definePlugin` на верхнем уровне модулей без этого флага. Перед включением
учесть единственный настоящий побочный эффект — `definePlugin` пишет контракт
плагина в `WeakMap` по классу: если приложение ставит библиотечный плагин
снаружи только по классу и нигде не импортирует его определение, сборщик
выбросит модуль, и `pluginProps` для него молча перестанут работать. Лекарство
— принимать в `usePlugins` определение (`AnchorPluginDescriptor`), структурно
оно уже подходит под `{ ctor, options }`.
