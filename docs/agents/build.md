# Версии и сборка пакетов

> Раздел корневого `AGENTS.md`, вынесен дословно, чтобы не грузиться в каждую
> сессию. Сквозные правила — в корне; этот файл читается перед задачей в своей
> области (см. «Где остальное» в корне).

## Версии пакетов

Библиотечные пакеты `@soldy-ui/*` — ядро, `setup`, `plugins`, адаптеры по
фреймворкам (`vue`, `react`, `angular`, `svelte`, `solid`, `webc`), тема и иконки — идут **одной версией**. Адаптеры жёстко привязаны к контракту
`core` и `setup`: отдельные версии пакетов дали бы только таблицу
совместимости.

Версии и `CHANGELOG.md` ведёт [changesets](https://changesets.dev), конфиг —
`.changeset/config.json`:

- **общую версию задаёт группа `fixed`** — в ней все библиотечные пакеты, и
  выпуск поднимает их вместе. У корневого `package.json` версии нет: changesets
  двигает только пакеты воркспейса, и версия корня после первого же выпуска
  стала бы устаревшей копией;
- **стенд (`@soldy-ui/playground-*`) — в `ignore`**: это инструмент, а не
  библиотека, он не выпускается и метаданных пакета не несёт. Новый стенд
  вносится в `ignore`, новый библиотечный пакет — в `fixed`. В обоих списках
  имена, а не glob: сторож сверяет их поимённо;
- **библиотечные пакеты выкладываются**: `private` у них нет, а
  `publishConfig.access` — `"public"`: у скоупа доступ по умолчанию
  `restricted`. Состав тарболла задаёт `files`, рядом с манифестом лежат
  `README.md` и копия корневого `LICENSE` — npm кладёт оба в тарболл мимо
  `files`. Стенд остаётся `private`. `privatePackages.version: true` всё равно
  обязателен: стенд им не версионируется, но и с ним в `ignore` флаг нужен
  changesets'у, чтобы не пропускать private-пакеты вовсе;
- **чужое содержимое — со своей лицензией.** Код пакетов — MIT, текст — копия
  корневого `LICENSE`. Пакет, который везёт чужое содержимое под другой
  лицензией, называет её в `license` выражением SPDX — `MIT AND Apache-2.0`,
  иначе сканер лицензий увидит одну MIT, — а её текст кладёт рядом с
  манифестом в `LICENSE-<идентификатор>` и вносит в `files`: сам npm кладёт в
  тарболл только `LICENSE`. Так устроены пакет иконок (см. «Пакеты иконок») и
  ядро — таблица первого дня недели из CLDR и таблица подсказок поля даты из
  React Spectrum (см. «Даты»): лицензий у ядра две чужие,
  `MIT AND Unicode-3.0 AND Apache-2.0`;
- **соседа пакет объявляет диапазоном от общей версии** — `"^0.1.0"`, и в
  `dependencies`, и в `peerDependencies`. Протокол `workspace:` npm не понимает
  вовсе (`EUNSUPPORTEDPROTOCOL` на `npm install`) — это pnpm и yarn. `"*"` тоже
  не годится: выпуск переписывает диапазон, только когда новая версия из него
  выпала, а из `"*"` не выпадает ничего — в опубликованном пакете он значил бы
  «любая версия ядра». Руками диапазоны не правятся: их поднимает
  `npm run changeset:version` вместе с версией.

**PR, который меняет файлы библиотечного пакета, несёт changeset** —
`.changeset/<имя>.md`, иначе задача CI `changeset` красная. Правке вне
библиотечных пакетов — `AGENTS.md`, CI, `tools/`, стенд — changeset не нужен.
В changeset — пакеты, чьи файлы менялись, и уровень:

- ломающее изменение — `minor` (`0.1.0` → `0.2.0`), остальное — `patch`;
  `major` до `1.0` не бывает;
- выпускать нечего — поменялись только тесты или инструменты разработки
  пакета — пустой changeset.

Файл пишет команда. С флагами она ничего не спрашивает, без флагов уходит в
интерактивные вопросы:

```bash
npm run changeset -- --patch @soldy-ui/core,@soldy-ui/setup -m "Что изменилось для потребителя"
npm run changeset -- --minor @soldy-ui/vue -m "Что сломалось и как обновиться"
npm run changeset -- --empty
```

Описание попадает в `CHANGELOG.md` пакета как есть. Проверка CI локально —
`npx changeset status --since=origin/main`; новый changeset она видит только
после `git add`.

**Выпуск** — по команде владельца `/release`: программист от свежего `main`
запускает `npm run changeset:version` и открывает PR `Выпуск <версия>` из
ветки `release/v<версия>`, мержит его владелец (порядок —
`.claude/agents/developer.md`, «Выпуск»). Команда поднимает версию группы,
собирает `CHANGELOG.md` из changeset'ов, удаляет их и обновляет
`package-lock.json`: версии воркспейсов записаны и там. Задача CI `changeset`
на ветках `release/*` не запускается — changeset'ы в выпуске уже удалены, и
она бы его уронила; поэтому ветка `release/*` — только для выпуска. Версии и
`CHANGELOG.md` руками не правятся, PR задачи версию не трогает.

Сторожит `packages/setup/__tests__/workspace-manifests.spec.ts`. Библиотечные
пакеты для него — пакеты из `workspaces` корневого манифеста, кроме `ignore`;
у каждого непустой `description`, `license` — `MIT` или `MIT AND <идентификатор>…`,
`repository.directory` совпадает с путём пакета, `version` задана. Цели `main`,
`types`, `style` и `exports` (вглубь) — файлы пакета, а цель, которую
игнорирует git, — выход сборки: она допустима, только если у пакета есть
скрипт `build`. Пакет открыт к публикации: `private` нет,
`publishConfig.access` — `"public"`, `files` непуст, рядом лежат непустой
`README.md` и `LICENSE`, совпадающий с корневым. На каждую чужую лицензию из
`license` рядом лежит непустой `LICENSE-<идентификатор>`, внесённый в `files`,
а текста лицензии, не названной в `license`, в `files` нет.
Каждый сосед `@soldy-ui/*` в любом поле зависимостей объявлен `^<его версия>`.
Версия у всех одна, у корня её нет; `fixed` — одна группа ровно из
библиотечных пакетов; каждое имя из `ignore` — пакет воркспейса; ни один
changeset не объявляет `major`, пока версия `0.x`. Новый пакет попадает под
проверку сам.

**Пакет объявляет всё, что импортирует.** Имя пакета из каждого голого
спецификатора в опубликованных файлах стоит в `dependencies` или
`peerDependencies` либо совпадает с именем самого пакета; подпуть
отбрасывается (`solid-js/web` → `solid-js`, `@angular/core/testing` →
`@angular/core`). `devDependencies` не в счёт: потребитель их не ставит. В
репозитории необъявленный импорт не виден — npm поднимает зависимости всех
воркспейсов в общий `node_modules`, — а из пакета, поставленного pnpm или Yarn
PnP, видно только объявленное. Так адаптер Angular импортировал
`@angular/common`, держа его в `devDependencies`. Исключений нет: `node:*` в
опубликованном пакете — такое же нарушение, и чинится оно манифестом пакета,
а не исключением в проверке.

Читается то, что уедет в npm, а не исходники: состав тарболла называет
`npm pack --dry-run` (пакет с `private` не уезжает), тексты берутся с диска.
Импорт — это `import` и `export … from` в любом виде, `import()` в коде и в
типах, `require()`, дополнение чужого модуля и `/// <reference types>` в JS,
декларациях и блоках `<script>` компонентов Svelte. Так виден импорт, который
вставил компилятор (`react/jsx-runtime`), и не виден кодоген, который в пакет
не попадает. Поэтому проверка идёт после сборки —
`npm run check:published-imports`, шаг CI «Импорты пакетов объявлены» сразу за
«Сборкой пакетов», — а не в `__tests__` пакетов: шаг «Тесты» идёт до сборки.
Несобранный пакет её не проходит: целей его точек входа (`main`, `types`,
`style`, `exports`) нет в тарболле. Сторожит `tools/published-imports/`:
правило — на фикстурах, воркспейс — собранным.

## Сборка пакетов

Наружу уезжает `dist`, а не исходники: `npm run build` из корня собирает
библиотечные пакеты по очереди, и у каждого скрипт `build` — два шага подряд
(у темы, с её вторым выходом, три; у адаптеров Svelte и Angular — один проход
своего инструмента, см. ниже).

```bash
npm run build                                    # все пакеты, по зависимостям
npm run build --workspace=@soldy-ui/core         # vite build, затем tsc
npm run build --workspace=@soldy-ui/svelte       # svelte-package: .svelte как есть + .d.ts
npm run build --workspace=@soldy-ui/angular      # ng-packagr: частичная форма и .d.ts
```

- **JS собирает Vite** по общей фабрике `tools/vite/lib.config.ts`: вход,
  `dist`, `formats: ['es']`, соседи по скоупу — external. Четыре копии одного
  конфига разъехались бы: `external: [/^@soldy\//]` у адаптера Vue пережил
  переименование скоупа и перестал совпадать хоть с чем-нибудь.
- **`.d.ts` собирает `tsc -p tsconfig.build.json`** — вторым шагом, потому что
  у Vite стоит `emptyOutDir` и обратный порядок стёр бы декларации. У конфига
  сборки `paths` пустой (кроме ссылки пакета на самого себя): сосед резолвится
  как пакет, через `node_modules` на свой `dist/index.d.ts`. Этим сборка и
  доказывает, что опубликованная поверхность самодостаточна. У адаптера Vue тем
  же конфигом ходит `vue-tsc`: `.vue` обычный `tsc` не читает, а декларация
  компонента (`Button.vue.d.ts`) лежит рядом с его модулем.
- **Порядок в корневом `build` — это зависимости, а не алфавит**: `core` →
  `plugins` → `setup` → `icons-material` → `theme-oren` → адаптеры (`vue`,
  `react`, `solid`, `webc`, `svelte`, `angular`). Сторожит
  `packages/setup/__tests__/workspace-manifests.spec.ts`: пакет, чьи точки
  входа ведут в выход сборки, обязан быть в корневом `build` и стоять раньше
  тех, кто объявил его в `dependencies`.
- **Адаптер Svelte собирает `svelte-package`** (`@sveltejs/package`) — одним
  проходом, бандла у него нет: `tsc` не читает `.svelte` вовсе. `.svelte`
  копируются как написаны, `.ts` транспилируются модуль в модуль
  (`useAdapter.svelte.ts` → `useAdapter.svelte.js`), а декларации
  (`Button.svelte.d.ts` и `.d.ts` модулей) выпускает `svelte2tsx` тем же
  проходом по `tsconfig.build.json` — с пустыми `paths`, как у всех.
  Компоненты заранее не компилируются: скомпилированный компонент привязан к
  `svelte/internal` своей версии, поэтому его, как и руны модулей
  `.svelte.js`, компилирует приложение потребителя. Отсюда `svelte` в
  `peerDependencies` — от 5.29, где появился `{@attach}`, — и условие `svelte`
  в `exports`: по нему плагин Svelte узнаёт библиотеку. Препроцессора и
  `svelte.config.*` у пакета нет: TS и в `<script lang="ts">`, и в разметке
  (`this={state.tag as string}`) Svelte 5 разбирает сам, поэтому `.svelte`
  уезжают теми же, что компилируют тесты пакета, а конфиг подхватили бы разом
  сборка, плагин Svelte в тестах и `svelte-check`. Черновик сборки
  (`.svelte-kit/`) — в `.gitignore`: перенести его можно только конфигом.
- **Адаптер Angular собирает `ng-packagr`** — одним проходом, командой
  `ng-packagr -p ng-package.json -c tsconfig.build.json`. Весь конфиг сборки —
  в двух файлах, которые названы в скрипте; цели в `angular.json` у неё нет,
  там живут опции прогона спеков (см. «Angular-специфика»). Библиотека Angular
  уезжает в **частичной форме** (`compilationMode: "partial"` в
  `tsconfig.build.json`): компоненты несут `ɵɵngDeclareComponent`, и компилятор
  приложения дособирает их под свою версию Angular, а полная форма
  (`ɵɵdefineComponent`) привязана к версии, которой её собрали. Ключ записан
  явно: с конфигом пакета без него `ng-packagr` собирает полную форму. `paths`
  у конфига пустой, как у всех: соседи и в коде, и в декларациях — по имени
  пакета. Формат выхода задаёт **Angular Package Format**, и «модуль на модуль»
  к нему неприменим: один FESM (`dist/fesm2022/soldy-ui-angular.mjs` — ESM, без
  минификации) и декларации, свёрнутые в один файл
  (`dist/types/soldy-ui-angular.d.ts`), — такой пакет и ждёт Angular CLI
  потребителя. Соседи лежат в `dependencies`, а `ng-packagr` пропускает там
  только `tslib`, поэтому в `ng-package.json` —
  `allowedNonPeerDependencies: ["^@soldy-ui/"]`.
- **У манифеста Angular нет `exports`.** `ng-packagr` строит свой манифест
  выхода из нашего и `exports["."]` пишет сам: наши условия `types` и
  `default` для него — конфликт, строку он перетирает. Точки входа — `main` и
  `types`, ровно те файлы, что его манифест называет в `exports["."]`.
  Выкладывается пакет, как все, из своего каталога: второй манифест
  (`dist/package.json`) и копии README и LICENSE, которые `ng-packagr` кладёт в
  `dist` для выкладки оттуда, `files` исключает.
- **Решения сборки проверяются по конфигу пакета, а не по фабрике.** Своя копия
  конфига рядом с пакетом расходится с фабрикой молча: у адаптера Vue такая
  копия держала формат `cjs` и складывала выход в `lib` мимо `dist`,
  объявленного в манифесте. Сторожит
  `packages/setup/__tests__/package-builds.spec.ts`. Рецепт пакета он узнаёт
  по инструменту в скрипте `build` (`vite build`, `svelte-package` или
  `ng-packagr`), и пакет очереди, который не подходит ровно под один, —
  падающий тест. У общего рецепта декларации идут после бандла, а бандл — ESM,
  модуль на модуль, без минификации и в `dist`. У рецепта Svelte вход `src`,
  выход `dist`, декларации не выключены и идут по `tsconfig.build.json`,
  `svelte.config.*` нет, а в `exports["."]` есть условие `svelte`. У рецепта
  Angular оба конфига названы в команде, `dest` конфига `-p` — `dist`, а
  `compilationMode` в `tsconfig.build.json` — `partial`. `tsconfig.build.json`
  у всех судится по опциям, которые действуют, — с учётом `extends`, как их
  читает сам TypeScript: соседей в `paths` нет, `preserveSymlinks` — тоже.
  Пакетный конфиг ведёт соседей в исходники, и конфиг сборки перекрывает их
  своим `paths`: без ключа они пришли бы по `extends`, как и
  `preserveSymlinks` из любого звена цепочки. Конфиг, который TypeScript не
  разобрал, — тоже падающий тест.
- **Выходов у пакета бывает два.** У темы это CSS (`dist/index.css`) и
  поведение — экспорт `./setup` (`dist/setup`); собираются они по очереди,
  каждый своим конфигом, и второй лежит в подкаталоге: `emptyOutDir` первого
  чистит весь `dist`. Отсюда опция `outDir` у фабрики. Отсюда же у темы
  второй скрипт, `build:css`: тему собирают и раньше соседей — первым шагом
  CI и внутри `npm run test:layout`, — а там нужен только CSS, и прогону
  деклараций `./setup` не на что опереться. Подробности —
  `packages/themes/oren/AGENTS.md`.

Три решения, о которые легко споткнуться:

- **Только ESM, без CJS.** Реестры плагинов и расширений узнают тип через
  `instanceof` («Плагины и расширения снаружи»), а двухформатный пакет даёт в
  одном приложении две копии класса — реестр молча перестал бы узнавать
  компонент.
- **Модуль на модуль, а не один файл** (`preserveModules`). Слепленный пакет
  теряет tree-shaking: приложение с одной кнопкой получало 420 KiB вместо
  224 KiB — вместе с дескрипторами Select, Tabs и Accordion. Сторожит второй
  тест `packages/setup/__tests__/tree-shaking.spec.ts`. Бандлер здесь нужен не
  ради одного файла, а ради спецификаторов: исходники импортируют соседние
  модули без расширений и папками (`export * from './components'`), а
  собранный `tsc`-ом пакет с такими путями в Node ESM не завёлся бы вовсе.
- **Минификации нет.** Библиотеку минифицирует сборщик приложения, а своя
  только коверкает имена классов, которыми подписаны ошибки сборки набора
  («TAriaPlugin уже входит в состав TButton»).

**Локальная разработка сборки не требует.** Тесты, стенд и проверки типов
ходят в соседей исходниками — алиасами в `vitest.config.ts` и `paths` в
`tsconfig.json`. Правка в ядре обязана быть видна без промежуточного билда,
поэтому на `dist` их не переводят. Новый пакет — новый алиас в тех, кто его
читает; алиас на папку пакета (`../../setup`) не годится: он резолвится через
манифест, то есть в `dist`. Путь — до файла входа (`../../setup/index.ts`).
Цели `paths` сторожит `packages/setup/__tests__/source-paths.spec.ts`: ни
один `tsconfig*.json` репозитория не ведёт в каталог с `package.json` — ни
точной целью, ни подстановкой в шаблон с `*`. Алиасы `vitest.config.ts` он не
читает.

Свой пакет — тоже исходниками. Тесты импортируют его по имени
(`import { Button } from '@soldy-ui/vue'`), и у пакета, чей `tsconfig.json`
берёт в программу `__tests__`, в `paths` есть ссылка на себя — в исходники:
`"@soldy-ui/vue": ["./src/index.ts"]`. Без неё имя уходило через
`node_modules` в манифест: без сборки «Типы — Vue» падали на «модуль не
найден», а со старой сборкой молча сверяли тесты с устаревшими типами.
Каталог с манифестом (`"."`, как было у setup) ведёт туда же, только
незаметно: пока `dist` нет, TypeScript откатывается на `index.ts` рядом.
Сторожит `packages/setup/__tests__/package-builds.spec.ts`: имя пакета из его
тестов TypeScript разрешает мимо манифеста и мимо `dist`, собран пакет или
нет.

**Предел, оставленный осознанно:** `.d.ts` — дерево с импортами без
расширений. У потребителя с `moduleResolution: bundler` (Vite, Next, любой
сборщик) они разрешаются, с `node16`/`nodenext` — нет (TS2834). Сворачивать
декларации в один файл сейчас не заводим. У адаптера Svelte без расширений и
сам JS: бандлера у него нет, и `export * from './components'` уезжает как
