# Замеры производительности

Как таблица soldy держит большой объём рядом с таблицами других библиотек. Файл —
журнал: новый замер дописывается новым разделом, старые не переписываются, чтобы
было видно, что дала каждая правка.

## Стенд

[`tools/bench-table/`](tools/bench-table/) — Vite-страница и прогонщик на Playwright.
Вне workspaces: зависимости других библиотек ставятся только в стенд и в монорепо не
попадают.

```bash
cd tools/bench-table
npm install                    # один раз: таблицы других библиотек
npm run bench -- 5000 3        # строк, прогонов, [библиотеки через запятую]
npm run bench -- 5000 3 soldy  # только наша таблица
npm run prof                   # профиль CPU soldy без минификации (5000 строк)
```

- `libs/data.ts` — данные и колонки, общие для всех: детерминированный генератор,
  20 колонок, `name` — строка, остальные — числа.
- `libs/<библиотека>.ts` — таблица библиотеки и селекторы её чекбокса «выбрать все» и
  заголовка сортировки. Новая библиотека — новый файл и строка в `main.ts`.
- `main.ts` — сценарии (`window.bench`), `run.mjs` — прогонщик и итоговая таблица.

## Методика

- Продакшн-сборка, Chromium (Playwright), окно 1600×1000. Новая страница на каждый
  прогон, в таблице — медиана.
- Время — от действия до момента, когда кадры снова идут чаще, чем раз в 50 мс, три
  кадра подряд: в него входят асинхронные досчёты библиотеки, а не только первый кадр.
- Действия — настоящие клики в DOM: чекбокс «выбрать все» в шапке, заголовок первой
  колонки.
- Память — прирост `usedJSHeapSize` после принудительной сборки мусора.
- У всех настройки по умолчанию, виртуализация выключена, ячейки — текст без своих
  рендереров. Прогонщик проверяет, что действие выполнилось: число отмеченных строк и
  первая строка после сортировки.

## 2026-10-09 — Vue, исходная точка

5000 строк × 20 колонок, 3 прогона. soldy — `main` на `453465a7`.

|                      | **soldy**    | Naive UI 2.45.3 | PrimeVue 5.0.2 |
| -------------------- | ------------ | --------------- | -------------- |
| Первый рендер        | 2,9 с        | **2,4 с**       | 23,5 с         |
| Память после рендера | 729 МБ       | **409 МБ**      | 2,8 ГБ         |
| Выделить все         | **1,7 с**    | 2,5 с           | 11,2 с         |
| Снять выделение      | **1,2 с**    | 2,6 с           | 10,8 с         |
| Сортировка ↑         | **1,5 с**    | 2,0 с           | 10,1 с         |
| Сортировка ↓         | **1,7 с**    | 2,0 с           | 9,1 с          |
| Замена данных        | **4,5 с**    | 5,1 с           | 11,1 с         |
| Размонтирование      | 0,45 с       | **0,27 с**      | 11,3 с         |
| DOM-узлов            | **125 тыс.** | 145 тыс.        | 130 тыс.       |

**Element Plus 2.14.7** замерен один раз и из стенда убран: рендер 9,1 с, память
580 МБ, «выделить все» 41 с, сортировка 46–91 с, замена данных 60 с. Прогон шёл
минутами и ничего не добавлял к сравнению.

Выводы:

- По скорости действий soldy впереди; в первом рендере на 0,5 с впереди Naive UI.
- Отставание одно — память: Naive UI держит ту же таблицу в 1,8 раза легче. У нас около
  146 КБ на строку, утечки нет (после размонтирования куча возвращается).
- Сортировка у нас почти целиком — пересчёт стилей и раскладки браузера после
  перестановки 5000 строк, наш JS там мал. Лечится только сокращением DOM.

Оговорки: одна машина, три прогона. Разница в 0,5 с близка к шуму, разница в разы — нет.
Первый клик сортировки у Naive UI — по убыванию, это её порядок. Память «после
размонтирования» у других библиотек (350–2260 МБ против наших 37) не сравнивается:
похоже на их кэши, а не на утечку — не исследовали.

## 2026-10-09 — Vue, выбор не перерисовывает ячейки строки

[869fekb4r](https://app.clickup.com/t/869fekb4r), PR
[#359](https://github.com/youra-h/soldy/pull/359). 5000 строк × 20 колонок, 5 прогонов.
«До» — разметка Vue с `main` на `4803c1ec`, «после» — ветка задачи. Замерены подряд на
одной машине, поэтому «до» чуть расходится с исходной точкой выше.

|                      | до       | после     |
| -------------------- | -------- | --------- |
| Первый рендер        | 2,9 с    | 2,9 с     |
| Память после рендера | 729 МБ   | 714 МБ    |
| Выделить все         | 1,9 с    | **1,3 с** |
| Снять выделение      | 1,3 с    | **0,8 с** |
| Сортировка ↑         | 1,6 с    | **1,0 с** |
| Сортировка ↓         | 1,7 с    | **1,1 с** |
| Замена данных        | 5,1 с    | 4,9 с     |
| Размонтирование      | 0,48 с   | 0,49 с    |
| DOM-узлов            | 125 тыс. | 125 тыс.  |

Что изменилось: ячейки строки во Vue — свой внутренний компонент, и слот `cell` доходит
до них стабильным пробросом (AGENTS.md, Pitfalls). Выбор перерисовывает строку — у неё
сменился `data-selected`, — но не её 20 ячеек, а перерисовка таблицы не трогает строки.

Выводы:

- «Выделить все» быстрее на 30 %, снятие — на 40 %, но не в разы, как ждали: перерисовка
  ячеек была только частью времени. Около половины оставшегося в «выделить все» —
  галочка чекбокса: CheckBox монтирует на каждую отметку компонент Icon со своим
  контекстом, на 5000 строк это 5000 монтирований. С пустой разметкой вместо Icon
  (ручной опыт, 3 прогона) «выделить все» — 0,7 с. Задача —
  [869feq9un](https://app.clickup.com/t/869feq9un).
- Сортировка ускорилась сильнее выбора, хотя её не трогали, — вывод исходной точки «наш
  JS там мал» был неверен. Слот `cell` таблицы ссылался на переменную цикла, слоты строк
  были динамическими, и любая перерисовка таблицы, перестановка строк тоже,
  перерисовывала все строки вместе с ячейками.
- Память — на 14 МБ меньше, хотя у каждой строки добавился компонент: таблица без слота
  больше не пробрасывает его строкам, и у каждой ячейки на один фрагмент слота меньше —
  минус 100 тыс. vnode и вдвое больше пустых текстовых узлов-якорей.
- Рендер, замена данных и размонтирование — в пределах шума.
- В профиле первого рендера около 0,5 с из 3 — сборка маршрутов событий при
  монтировании каждого компонента: участника события ищут перебором всех пропсов и
  триггеров. Задача — [869feqa1t](https://app.clickup.com/t/869feqa1t).
