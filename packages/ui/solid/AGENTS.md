# Адаптер Solid

> Читается перед задачей в `packages/ui/solid` (см. «Где остальное» в корне).
> Сквозные правила — в корневом `AGENTS.md`; здесь — то, что у Solid своё.
> Комментарии в коде адаптера и компонентов — короткие шапки со ссылкой сюда.

## Solid-специфика

Тело компонента Solid выполняется один раз, на сервере тоже, а разметка
читает состояние там, где его прочли: в выражении JSX и спреде — аксессором,
в теле — один раз. Почти всё ниже следует из этого.

### Помощники адаптера

Компонент собирает контекст через `createSolidAdapterContext`
(`src/adapter/common/`): локаль ближайшего `LocaleProvider` и id
монтирования — `createUniqueId()`. Он совпадает на сервере и при гидратации
и зовётся из любой функции тела, поэтому его берёт обёртка, а не компонент.
Контекст на чужом наборе (`config.bundle` — фасад коллекции) их не берёт: id и
локаль у того, кто набор собрал, и у компонента с двумя контекстами id один.
Сборку мимо обёртки ловит сторож `framework-mechanisms-components.spec.ts`:
`createAdapterContext` из `@soldy-ui/setup` в компонентах Solid запрещён.

Чего тело компонента само не может, дают помощники адаптера:

| Помощник                        | Что даёт                                                                                     |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| `createRootProps`               | атрибуты корня мемо (см. «Раскладка корня»)                                                  |
| `createWrappedRootProps`        | обёртка и корень внутри неё (окно таблицы вокруг `table`), `ref` — `consumerRef` и `bindRef` |
| `createPartProps`               | набор части (`labelAria` подписи Field) или атрибуты потребителя контролу                    |
| `rootElement` из `useAdapter`   | привязанный корень узлом — якорь панели Popover, Tooltip, Menu, Select                       |
| `toPartClass`                   | классы части без своего экземпляра строкой для `class` (панель Menu на Frame)                |
| `resolveSlot`                   | слот, по которому разметка выбирает запасное (текст Button)                                  |
| `liveScope`                     | scope слота, чьё содержимое переживает его смену                                             |
| `fieldText`, `textareaText`     | текст поля, который пишется в узел, только когда разошёлся с ним                             |
| `useElevator`, `Elevate`        | лифт сборки и слой детям (см. «Лифт»)                                                        |
| `ResolvedSlot`                  | слот владельца, развёрнутый под его слоем, и со scope                                        |
| `KeyedFor`                      | петля по ключу записи: `drawn` и секции `sections`                                           |
| `relaySlot`                     | проброс слота элемента: scope элемента и сам элемент — живыми полями                         |
| `useCollectionAdapter`          | адаптер фасада коллекции: его состояние и атрибуты, которые он не съел                       |
| `joinBindings`                  | связка компонента с фасадами — одна: состояние одним видом (`joinState`)                     |
| `chainHandler`                  | своё, затем обработчик потребителя — на одном событии разметки                               |
| `Show`, `For`, `Index` (`flow`) | ветки и петли, которые переживают окна гидратации                                            |

**Спред на узле разметки компонента** (на нативном элементе и на `Dynamic`) —
только от этих помощников: `{...x()}`, `{...x().поле}` или `{...x}`, где `x` —
`const` из `createRootProps`, `createWrappedRootProps`, `createPartProps`,
`fieldText` или `textareaText`. Прямой спред состояния
(`{...state.contentAria}`) смену за гидратацию до узла не донёс бы; его ловит
блок eslint `soldy/solid-part-props` (правило —
`tools/eslint/rules/solid-part-props.ts`). Ветки и петли — примитивы адаптера,
а не Solid: импорт их из `solid-js` в компонентах ловит блок eslint
`soldy/solid-components-flow`.

### Связка

`useAdapter` (`src/adapter/runtime/useAdapter.ts`) связывает контекст с
Solid через обмен `adapter.connect()`:

- состояние — неглубокое (`createShallowState`, `src/adapter/runtime/state.ts`):
  сигнал на свойство, значение отдаётся как есть; подписка на связку сразу
  отдаёт значение каждого свойства. Стора Solid здесь нет: он оборачивает
  каждый вложенный объект в прокси с сигналом на прочитанное свойство, а ядро
  отдаёт значения, и сменившееся приходит новым объектом (корневой
  `AGENTS.md`, «Контракт границы core → ui»). В таблице стор держал около двух
  десятков сигналов на ячейку — ячейку, её `aria` и `dataset` — и 1,28 ГБ на
  5000 строк против 728 МБ без него (benchmarks/table_solid.md). Как
  `shallowRef` у Vue. Значение-функцию запись отдаёт сигналу обёрткой: сеттер
  счёл бы её updater'ом. Свойство со значением `undefined` — незаданное, `in`
  его не видит. Сторожит «состояние связки» в `__tests__/adapter.spec.tsx`;
- входы — эффект над всеми пропсами, связка пишет из них сменившиеся. Пропсы
  Solid — объект геттеров: деструктурировать нельзя, читать напрямую — можно;
- события — колбэк-пропсы `onXxx`;
- приём (`attach()`) — в теле: дети выполняются в порядке документа, и
  элементы разметки входят в коллекцию в порядке DOM. Очистки Solid зовёт в
  обратном порядке, и фасад уходит раньше компонента.

**`ref`.** У узла `ref` один, и ставит его адаптер: `ref` привязывает корень к
`TElementPlugin` и тем же вызовом отдаёт узел `ref` потребителя. Компонент
ставит его последним, после спреда атрибутов: `ref` потребителя из его
атрибутов не должен выбить привязку (не было бы `element:ready`), поэтому
раскладка корня `ref` потребителя снимает. В мемо атрибутов `ref` тоже не
входит: Solid перечитывал бы его на каждую смену атрибута, отвязывая и заново
привязывая узел. `ref` потребителя — всегда корень, у поля тоже (a11y.md,
«`ref` потребителя — корень компонента»). Отвязка — очисткой владельца узла:
смена тега (`Dynamic`) отвязывает прежний и привязывает новый, а сигнал
`rootElement` проходит через `null`. Снятие узла Solid своим `ref` не
объявляет, и `ref` потребителя тоже. Корень внутри обёртки получает половины
по отдельности: корню `bindRef`, обёртке `consumerRef`.

**Коллекция: два контекста — одна связка.** Ответственности разведены, как в
Angular: `useCollectionAdapter(facade, props, forward)` — адаптер фасада
(входы и события из `props`, атрибуты — из остатка `forward` компонента или
предыдущего фасада, своих `ctrl` и `ref` нет), а `joinBindings(owner,
...facades)` сводит связку компонента с фасадами в одну: состояние разметка
читает одним видом — `joinState`, атрибуты — последнего фасада, остальное —
компонента. Вид — прокси, а не спред и не геттеры: спред прочёл бы состояние
один раз, в теле, а свойство со значением `undefined` состояние незаданным
и считает, и геттеры по ключам потеряли бы свойства, незаданные к сборке.
Одноимённых свойств у компонента и фасада нет — имена фасада префиксуются.
Третий контекст (`Menu.Submenu`: свой, пункт в меню над ним, меню своих
пунктов) — второй фасад в `joinBindings`: меню отбирает атрибуты из остатка
пункта.

### Раскладка корня

Solid атрибутов компоненту не наследует: класс, стиль и атрибуты сливает
разметка, одной раскладкой на все компоненты (`src/adapter/common/root.ts`,
как `toRootProps` у React и Svelte). Порядок слоёв:

- атрибуты — наборы ядра (`attrs`, `aria`, `dataset`, в порядке Vue), поверх
  них атрибуты потребителя: `tabindex="-1"` строки списка перекрывает
  `tabindex="0"`, который кнопка на `div` ставит себе сама. Имена HTML и
  `null` Solid понимает сам;
- `class` — классы ядра, затем потребителя;
- `style` — выход плагина раскладки (`layout_styles`), стиль-выход компонента
  (`fractionStyle`), место элемента коллекции (`order`), поверх — стиль
  потребителя, поверх всего — `display: none` скрытого корня, как `v-show`.

Стиль — объект с именами как в CSS (`z-index`, `--*`). Solid ставит его по
свойству и не трогает того, что плагины пишут в узел сами
(`--so-swipe-offset`), поэтому пустой стиль — тоже объект: `undefined` снял бы
атрибут целиком. Пустое значение (`width: ''`) свойства не задаёт — сервер
напечатал бы `width:`. Стиль потребителя строкой разобрать негде (на сервере
нет документа), и тогда слои склеиваются текстом; такой стиль Solid пишет
целиком, и записанное в узел мимо разметки его смену не переживает.

У поля (Input, CheckBox, Switch) атрибуты потребителя делятся, как
`useSplitAttrs` у Vue: класс и стиль — корню (`toRootForward`), остальное —
`<input>` (`toControlAttrs`), поверх `aria` поля. Так же делят элемент
коллекции (остальное — строке, у радио — полю), ListBox и Tabs (остальное —
узлу с ролью). Окно таблицы — так же: обёртке класс, стиль и скрытие, корню
`table` остальное. Состояние корню внутри обёртки отдаётся поимённо: остаток
деструктуризации прокси-состояния пуст.

Радио корню состояние отдаёт без `order`: группа радио не раскладывает, и
номер увёл бы радио по чужому флекс-ряду — как у Vue, где у радио нет
привязки `order`.

### Окна гидратации

Окно гидратации — время, пока Solid сверяет разметку сервера с тем, что
собирает браузер (`sharedConfig.context`). Кроме основного (`hydrate()`) это
граница `Suspense`, дослана потоком (`renderToStream`), когда пришли её
данные, и остров со своим `hydrate()`. Пока окно открыто, Solid считает
совпавшими с сервером все узлы документа, не только своего окна
(`isHydrating` смотрит на `isConnected`):

- в узлы не пишет — ни атрибутов, ни класса, ни свойств, ни текста, а спред
  запоминает пропущенное как записанное и потом пишет только разницу со своей
  памятью;
- не снимает узлы у подключённого родителя и не вставляет новые;
- новый элемент ищет по ключу гидратации текущего окна — под ним чужой узел
  или никакого: в разработке `Hydration Mismatch` и срыв гидратации, без
  `development` — элемент мимо разметки и падение `Dynamic`.

Вход элемента коллекции меняет то, что браузер уже собрал: в основном окне —
узлы выше него (таб выше активного отдаёт остановку Tab), в позднем — и узлы
вне границы. Поэтому мемо адаптера — раскладка корня и частей, ветки и петли —
стоят на одном помощнике `createHeldMemo` (`src/adapter/common/hydration.ts`):

- первое значение — живое. Собранное в окне, мемо считает его в той же
  точке, что сервер, и оно совпадает с разметкой;
- пересчёт в любом окне — и своём, и чужом — читает источники и до конца окна
  отдаёт прежнее: память спреда остаётся равной узлу;
- конец окна мемо узнаёт эффектом, который заводит в таком пересчёте:
  пользовательские эффекты Solid выполняет, уже сняв контекст гидратации.
  Сигнал конца один на документ, и живое отдают разом все мемо, что держали
  прежнее; спред дописывает разницу уже вне гидратации;
- не пересчитанное за окно ничего не ждёт: его значение и так живое.

Придержать само состояние — одним местом на все привязки — нельзя: сервер печатает
в порядке документа, и структура после детей видит у него то, что дети уже
сменили (слот пустого ListBox после элементов сервер не печатает). Первое
чтение структуры обязано быть живым; удерживается только запись в узел.

`createPartProps` вне гидратации отдаёт само чтение — мемо на каждую часть,
у таблицы на каждую ячейку, не окупается, — а вызванный в ней даёт то же
мемо. Зовут его там, где узел рисуется (в теле, у узла на запись — в функции
петли), а не в выражении спреда: там он собирал бы мемо на каждый пересчёт.
Одиночные привязки (`id={state.id}`) и текст вне помощников: их смены во
время гидратации нет. Набор части, нарисованной браузером без гидратации
(панель слоя), мемо не держит: смену в чужом окне Solid на таком узле теряет,
но библиотека её не порождает — что коллекция пишет на вход соседа, ложится
на корень элемента, а его раскладку мемо держит в любом окне.

Как это видно на коллекциях — docs/agents/collections.md, «Цена». Сторожат
спеки `__tests__/hydration/` — `late`, `list-box`, `structure`,
`browser-drawn`, `part-props`, `collections`, `field`.

### Ветки и петли

`Show`, `For` и `Index` компонентов — примитивы адаптера
(`src/adapter/runtime/flow.ts`), `KeyedFor` — рядом. Вне окна это клиентские
примитивы Solid 1.9 с тем же числом вычислений и ключами гидратации у детей,
на сервере — сами примитивы Solid. Мемо условия и отображения держат окно,
как мемо раскладки: ветка не сменяется, новых строк нет, записи не
обновляются; после окна Solid строит и снимает узлы уже вне гидратации. Так
переживают окно панель таба, ставшая активной, слот пустого списка, тост в
регионе, который браузер нарисовал сам. В бочку адаптера модуль не входит:
имена столкнулись бы с `solid-js` у потребителя. `Switch` и `Match`
компонентам пока не нужны.

Вне правила — тег корня (`Dynamic`) и текст (их меняет проп приложения) и
ветки `Teleport` на `Show` Solid: содержимое портала Solid рисует после окна
сам.

`KeyedFor` держит узел, пока в списке есть запись с его ключом, и отдаёт ему
новую запись аксессором: `drawn` коллекции — новые записи на каждую смену, и
`For` по ссылке пересоздавал бы строки вместе с фокусом. Строки живут в своих
корнях под владельцем петли — внутри `Elevate` они видят слой владельца.

Ячейка таблицы — узел на запись тысячами, и `Dynamic` на ней не стоит: он
давал ячейке два прокси (`mergeProps` и `splitProps`), два мемо и три эффекта
`spread` — больше половины времени сборки строк. Тег ячейки (`th` заголовка
строки или `td`) выбирает ветка в теле функции петли, а `rowHeader` входит в
ключ петли ячеек: сменился — ячейка новая, как у `Dynamic` со сменой
`component`. Три набора ячейки (`dataset`, `cellAria` таблицы, `aria`) —
одним `createPartProps`. Сторожит «rowHeader колонки сменился» в
`__tests__/table.spec.tsx`.

### Слоты

Слот без scope — готовые узлы, со scope — ещё и функция. Функцию слота
отличает арность: ленивое мемо компилятора — тоже функция, но без
параметров. Геттер слота в пропсах Solid на каждое чтение создаёт узлы
заново, поэтому слот, по которому разметка что-то решает, читают один раз:

- `resolveSlot` — разворот в теле; пустой — по узлам: компонент в слоте,
  который ничего не нарисовал, уступает место запасному (DatePicker отдаёт
  полю кнопку очистки, пустую без `clearable`);
- `ResolvedSlot` — разворот там, где стоит в разметке, под `Elevate`
  владельца коллекции: развёрнутый в теле, слот собрал бы элементы вне его
  слоя. Задан ли слот, решает значение, а не узлы — компонент в слоте
  содержимое, что бы ни нарисовал, как VNode у Vue. Иначе элемент разметки,
  удалённый из коллекции, пока смонтирован, переключил бы владельца на
  элементы из данных (`change:items` приходит после `item:removed`), и
  экземпляр вошёл бы снова невидимым.

Scope функция слота получает живым (`liveScope`): объект с геттерами по
ключам первого чтения. Свежий объект scope перезапускал бы функцию на каждую
смену, и Solid пересоздавал бы то, что она нарисовала: подсказку ручки
Slider на каждый шаг, содержимое пункта ListBox на выбор, триггер Popover на
открытие — с потерей фокуса. Прочитанное в разметке слота (`scope.text`,
спред `scope.triggerAria`) обновляется на месте; прочитанное в теле функции
(деструктуризация, условие) функцию перезапускает. Тип scope — значения, как
в дескрипторе.

`relaySlot` пробрасывает слот владельца в слот элемента: scope элемента
плюс сам элемент, живыми полями. Не задан — `undefined`, и элемент рисует
своё. Проброс — функция с параметром, иначе его сочли бы готовым
содержимым.

### Лифт

Контекст Solid детям отдаёт только `Provider`, и императивно его не
выставить: своего владельца у компонента в продакшене и на сервере нет, и
значение в `getOwner()` увидели бы соседи. Поэтому лифт — слои
(`src/adapter/elevator/`): контекст один на все ключи, как у React и Angular;
слой — свои значения поверх слоя предка, как у Angular (сборка одна, следить
за прочитанным незачем). Опущенный `null` — тоже значение
(`TVirtualCollectionExtension`). `useElevator()` в теле читает слой предка и
даёт фабрику лифтов (`up()` — слой предка, `down()` — свой) и свой слой;
детям его отдаёт `Elevate`, а пустой слой провайдера не ставит — флажок в
каждой строке таблицы своего не опускает. `useToasts()` берёт API `up()` из
того же слоя, поэтому зовётся в теле компонента под менеджером. Подробно —
docs/agents/collections.md, «Лифт Solid».

### Текст поля

Привязку `value` Solid пишет в узел на каждую смену, с узлом не сверяя. Запись
из кода снимает с поля пометку «изменено пользователем», и браузер перестаёт
проверять `minlength` и `maxlength`. Поэтому `value` в атрибуты поля не идёт:
`fieldText` ставит `ref`, эффект которого пишет текст, только когда он
разошёлся с узлом. Эффект пользовательский: Solid выполняет его после
атрибутов, а `range` прижимает значение к `min` и `max` (сторожит «полоса с
полем» в `__tests__/table.spec.tsx`). На сервере текст уходит атрибутом
`value`, у `<textarea>` — содержимым (`textareaText`): атрибута `value` у неё
нет, а `textContent` в браузере сменил бы умолчание поля. Отметку флажка
Solid пишет свойством, и совпавшая запись ничего не снимает.

### Teleport

`Teleport` (`src/adapter/runtime/Teleport.tsx`) — аналог `<teleport :to>`
поверх `Portal`: без цели содержимого нет (на сервере тоже), `disabled`
рисует на месте. Содержимое разворачивается один раз — мемо под владельцем
Teleport, с первого чтения, — и обе ветки читают его: смена цели или
`disabled` переносит те же узлы, поле в панели сохраняет набранное. Заведённое
сразу, мемо собирало бы содержимое без цели или по разметке, которой сервер
не рисовал. Обёртку `div` `Portal` кладёт в цель — плагинам оверлея она не
мешает: панель они находят по `data-owner`, слой — по `closest`.
