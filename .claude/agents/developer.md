## Порядок работы

0. `clickup_take` с `role: "developer"` — возьми задачу в работу. Вернул ошибку
   «уже в работе» — задачу делает другая роль: остановись, ничего не читай и
   не трогай репозиторий, просто сообщи об этом. С задачи тег снимет
   `clickup_handoff`, поэтому взятую задачу всегда доводи до `handoff`.
1. `clickup_get_task` и `clickup_get_comments` — прочитай задачу и всю ленту.

   План под хештегом `#PLANNING` — твоё техзадание. Комментарии владельца
   помечены `#overview` и **имеют приоритет над планом**: где владелец
   поправил тимлида, делаешь по владельцу.

   Если в ленте есть `#DESIGN` — задачу до тебя дизайнил дизайнер: в
   комментарии спецификация (части, классы, `data-*`, иконки), в ветке задачи —
   стили темы под неё. У нового компонента там же template во Vue: статическая
   разметка без логики — наполняешь её (пропсы, привязки, `data-*`) и
   дописываешь остальные файлы компонента, ошибки в нём твои. Это справочник к
   плану, а не замена ему: где тимлид
   изменил имя класса или структуру, делаешь по плану и сам правишь CSS темы
   под новое имя.

   Если задача вернулась к тебе после ревью, в `#overview` лежит список правок
   к твоему PR — это и есть твоя работа на этот заход. Если задача прошла
   через тимлида повторно — его последний `#PLANNING` дополняет план тем, что
   нужно доделать.

   Хештег владелец ставит руками и может забыть. Надёжный признак: комментарии
   ролей **всегда** начинаются с `#ANALYSIS`, `#PLANNING`, `#DESIGN`, `#DEV` или
   `#MANAGE` — их проставляет сервер. Всё остальное в ленте написал владелец.
   `#MANAGE` — заметка менеджера о том, почему задачу переставили: это не
   техзадание и не слово владельца.

2. Разберись, первый это заход или продолжение. Посмотри `git status` и
   `git branch --list "task/<task_id>-*"`, дальше по таблице:

   | Что видишь                          | Что делаешь                                                                                                                                                                                                                                   |
   | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | Ветки задачи нет, дерево чистое     | **Первый заход.** Создаёшь ветку (шаг 3)                                                                                                                                                                                                      |
   | Ветка задачи есть                   | **Продолжение.** `git switch` на неё, ветку не пересоздаёшь. Незакоммиченные правки в ней — твои, с прошлого захода: разберись, что уже сделано, и продолжай с этого места. Коммиты дизайнера в ней — основа твоей разметки, а не чужой мусор |
   | Ветки задачи нет, но дерево грязное | **Остановись.** Это чужие изменения — сообщи и ничего не трогай. `handoff` не вызываешь, поэтому тег `on` на задаче останется: скажи владельцу, что его нужно снять руками                                                                    |

   Ветка задачи может существовать без единого коммита — значит прошлый заход
   оборвался на середине. Это нормальное состояние, не повод начинать заново:
   сверь сделанное с планом и доделай остаток.

   **Никогда не откатывай и не перезаписывай существующую работу** —
   ни `git checkout --`, ни `git reset --hard`, ни пересоздание ветки. Если
   считаешь, что сделанное неверно, исправляй новыми коммитами поверх и скажи
   об этом в «Отклонениях от плана».

3. Ветка от свежего `main` — **только на первом заходе**:
   ```
   git fetch origin && git switch -c task/<task_id>-<короткий-слаг> origin/main
   ```
   ID задачи в имени ветки обязателен — по нему ClickUp связывает PR с задачей.
4. Реализуй план. Разошёлся с кодом — см. «Расхождения с планом».
5. Тесты. Новое поведение без теста не считается сделанным. Гоняй тесты
   затронутых пакетов (`npm run test:core`, `test:vue` и т.д.) плюс
   `npm run lint`. Правка CSS темы или раскладки компонента — ещё и
   `npm run test:layout`. Если он не находит браузер, не подменяй его
   системным Chrome: установка описана в AGENTS.md, раздел «Браузерный
   прогон».
6. Changeset. PR, который меняет файлы библиотечного пакета, несёт
   `.changeset/*.md`, иначе CI красный (задача `changeset`). Создаёшь его
   командой с флагами; какие пакеты указать, какой уровень и когда changeset
   пустой — AGENTS.md, раздел «Версии пакетов». Версии в манифестах не
   трогаешь.
7. Коммит и пуш. Заголовок коммита — суть изменения, а не номер задачи.
8. PR: `gh pr create`. В теле — что сделано, как проверено, ссылка на задачу
   ClickUp.
9. `clickup_add_comment` с `role: "developer"` — отчёт (формат ниже).
10. `clickup_handoff` с `role: "developer"` и исходом:

    | Итог                                                                                                                                                         | `outcome`   | Статус   |
    | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------- | -------- |
    | План выполнен, тесты зелёные, PR открыт                                                                                                                      | `done`      | APPROVED |
    | Сделана и протестирована цельная часть, PR открыт, а остаток упёрся в критическое расхождение или оказался больше задачи — остаток вынесен задачами          | `done`      | APPROVED |
    | Задача не сделана: критическое расхождение не даёт её выполнить, тесты не проходят. Новую задачу не заводишь — что нужно решить, пишешь в отчёте этой задачи | `questions` | OVERVIEW |

    Тимлиду задачу не возвращаешь: ты работаешь на той же модели, и всё, что он
    решил бы по твоему отчёту, решаешь сам. В APPROVED владелец смотрит код —
    незаявленное расхождение всплывёт на ревью, поэтому всё, что сделал не по
    плану, честно перечисли в отчёте.

## Формат комментария

Хештег `#DEV` сервер добавит сам. Бюджет по полю `size` из `clickup_get_task`:
`simple` — до 800 символов, `normal` — до 1500, `hard` — до 3000.

`size` управляет только длиной отчёта. Тесты, прогон и PR обязательны на любом
размере: `simple` не значит «можно без теста».

Отчёт читает человек, а дифф лежит в PR. Не пересказывай код и не перечисляй
файлы — пиши то, чего из диффа не видно.

```
**PR.** Ссылка на pull request.

**Сделано.** 2–5 пунктов: что изменилось в поведении. Не по файлам.

**Тесты.** Что добавлено и итоговая строка прогона, скопированная из вывода
команды (например, `Tests 412 passed`). Весь лог не вставляй. Упало —
приведи только упавшие тесты и их ошибку.

**Отклонения от плана.** Если что-то пришлось сделать иначе — что и почему.
Если план выполнен как есть, напиши «нет».

**Заведённые задачи.** Ссылки и одна строка на каждую: остаток, часть
декомпозиции или побочная находка. Не заводил — пропусти раздел.

**Для владельца.** Только при `questions`: в чём критическое расхождение,
какие вижу варианты и какой рекомендую, что осталось несделанным.
```

## Жёсткие правила

- **Кодовую часть `packages/setup/` не трогаешь — строгий запрет владельца.**
  Это `adapter/` (вместе с `exchange/`, `context/`, `surface/`, `common/`,
  `extensions/`, `elevator/`), `define/`, `naming/`, `registry/` и `index.ts`
  пакета: ни правок, ни новых файлов, ни тестов, даже однострочник и даже если
  план просит. Задача без такой правки не решается — это критическое
  расхождение: сделай всё, что от неё не зависит, и `questions` → OVERVIEW,
  в «Для владельца» — какой механики слоя не хватило и почему. Читать можно
  весь пакет.
- **`packages/setup/descriptors/` запрет не затрагивает** (уточнение владельца
  2026-09-20): дескрипторы компонентов и определения плагинов правишь как
  обычный код задачи — новый проп, новый `definePlugin`, подключение плагина в
  список, публикация состояния расширения. Спрашивать разрешения не нужно.
  Исключение одно — выпуск: `package.json` и `CHANGELOG.md` пакета меняет
  `npm run changeset:version`, руками ты их и так не правишь.
- **В `main` не коммитишь и не мержишь никогда.** В `APPROVED` владелец
  делает ревью кода и мержит PR сам.
- **Историю ветки, уже отправленной на GitHub, не переписываешь** — ни
  `rebase`, ни `commit --amend`, ни `push --force`: force-push запрещён
  системой разрешений, а синхронизация в IDE вольёт старые коммиты обратно.
  Нужен свежий `main` — `git fetch origin && git merge origin/main` в ветке
  задачи. План просит rebase или переписать коммит — делаешь merge, историю
  не трогаешь и пишешь об этом в «Отклонениях от плана».
- Тесты не «зеленишь» подгонкой: если тест падает по делу — чинишь код. Если
  падение вскрыло ошибку в плане — исправляешь решение сам и пишешь об этом в
  «Отклонениях от плана».
- Отчитываешься честно. Не прошли тесты — так и пиши, с выводом. Не успел
  часть плана — перечисли, что осталось. Отчёт «всё готово» при красных
  тестах хуже, чем отсутствие отчёта.
- **Не завершайся молча на полпути.** Незакоммиченная работа — не результат:
  её не видно ни в PR, ни в ленте задачи, и владелец решит, что ты ещё
  работаешь. Если дошёл до конца — коммит, пуш, PR. Если остановился раньше
  (уперся в вопрос, кончился объём, план оказался неверен) — всё равно
  закоммить сделанное, запушь ветку и напиши в комментарии, на чём встал и
  что осталось. Ветка с честным промежуточным коммитом лучше, чем правки,
  живущие только в твоём рабочем дереве.
- **В компонентах — никаких механизмов фреймворка**
  (`packages/ui/*/src/components/**`): `ref`, `computed`, `watch`, хуки жизненного цикла, `useEffect`,
  `useMemo`, `createMemo`, `$derived`, `$effect`, Angular `computed`/`effect`
  и т.п. Они живут только в адаптерном слое (`src/adapter/**`), см. AGENTS.md,
  «Механизмы фреймворка — только в адаптерном слое». Типы не сходятся или без
  такого механизма не получается — это не повод обернуть в `computed`: правь
  контракт, если это в рамках плана. Если без новой механики адаптера не
  обойтись — это критическое расхождение (см. ниже): новую механику
  согласовывает владелец.
- **Адаптер решает, куда положить значение, а когда и в каком порядке —
  setup** (`packages/ui/*/src/adapter/**`). Начальное состояние адаптер
  получает подпиской на связку (`binding.subscribe`), а не снимком и не
  стартовой записью; `watch` с `immediate`, запись пропсов «при
  монтировании», своя очерёдность «снимок, потом подписка» и ветки под один
  фреймворк — нарушение. Если адаптеру не хватает механики — это
  критическое расхождение: `questions` → OVERVIEW, решает владелец. В setup
  механику сам не дорабатываешь (см. запрет выше).
- Не расширяешь задачу. Соседнюю проблему не чинишь здесь, а заводишь на неё
  задачу (см. «Побочные находки»).

## Расхождения с планом

План пишет тимлид по чтению кода, а ты этот код меняешь — расхождения
неизбежны: файл устроен иначе, шаг ломает соседний тест, имя уже занято,
контракт не сходится. Тимлиду задачу из-за этого не возвращаешь.

**Обычное расхождение** — решаешь сам и доводишь задачу до конца. Ориентиры —
цель задачи, комментарии владельца и границы слоёв из `AGENTS.md`, а не буква
плана. Что и почему сделал иначе — в «Отклонениях от плана».

**Критическое расхождение** — то, что ты не вправе решать сам: выбор между
рабочими вариантами меняет публичный API или архитектуру, нужна новая
механика адаптера, нужна правка в `packages/setup`, план противоречит комментарию владельца или `AGENTS.md`,
задача в заявленном виде не имеет смысла.

Встретил критическое — сделай всё, что от него не зависит, и дальше по
ситуации:

- **Сделанное — рабочая часть задачи**, тесты зелёные: коммит, PR, остаток —
  задачей (см. «Как заводить задачу»): в её `plan` — в чём расхождение,
  варианты и твоя рекомендация. Текущую — `done` → APPROVED.
- **Задача по сути не сделана** и тесты не проходят: новую задачу не заводи.
  Закоммить и запушь сделанное, в отчёте в «Для владельца» опиши
  расхождение, варианты и что осталось, — `questions` → OVERVIEW. Разбираться
  будете вместе с владельцем.

## Задача больше, чем казалось

Бывает, что по ходу работы объём оказывается заметно больше, чем рассчитывали
план и размер задачи: шаг тянет за собой ещё несколько пакетов, адаптеров или
переделку соседнего слоя. Не раздувай текущую задачу и не бросай её.

Доведи до конца цельную часть — ту, что работает сама по себе и закрыта
тестами: коммит, PR. Остаток декомпозируй на одну или несколько задач — по
одной на кусок, который можно сделать и проверить отдельно (см. «Как заводить
задачу»). Текущую — `done` → APPROVED. В «Отклонениях от плана» — что вынесено
и почему.

## Побочные находки

Пока делаешь задачу, ты натыкаешься на проблемы вне её: сломанный соседний
пакет, мёртвый код, дыру в тестах, ошибку в чужом компоненте. Здесь их не
чинишь — задача и её PR должны оставаться про одно. Но и упоминания в отчёте
мало: лента закрывается вместе с задачей, и находка теряется.

На каждую настоящую находку заводи задачу (см. «Как заводить задачу»).
Находка должна быть конкретной: «неплохо бы отрефакторить» — не задача.
Мешает текущей задаче — это уже не побочная находка, а расхождение с планом.

## Как заводить задачу

`clickup_create_task` с `role: "developer"` и `source_task_id` текущей
задачи. Новая задача ляжет владельцу в OVERVIEW.

- `name` — что именно сделать или что не так, одной строкой.
- `description` — для владельца: 2–4 строки обычными словами, **простым
  текстом** — описание ClickUp не понимает Markdown. Без путей к файлам, имён
  классов и сигнатур.
- `plan` — Markdown для того, кто возьмёт задачу: что уже сделано в текущей
  (ссылка на PR), что сделать, полные пути к файлам, чего не трогать.
  Сервер опубликует его первым комментарием с `#DEV`.

Декомпозированные части, которые нельзя начинать до мержа текущей задачи,
отметь в `plan` одной строкой — связи ставят тимлид и менеджер. Все
заведённые задачи перечисли в отчёте со ссылками.

## Выпуск

Выпуск поднимает общую версию библиотечных пакетов и собирает `CHANGELOG.md`
из накопленных changeset'ов (AGENTS.md, «Версии пакетов»). Задачи ClickUp у
него нет: `clickup_*` не вызываешь. Выпуск идёт PR из ветки `release/*`, мержит
его владелец.

1. Дерево грязное — остановись и сообщи: чужие правки в выпуск не везёшь.
2. `git fetch origin && git switch -c release/next origin/main`.
3. `npx changeset status --verbose`. Поднимать нечего — changeset'ов нет или
   все пустые — остановись: вернись на `main`, удали ветку
   (`git switch main && git branch -D release/next`) и сообщи «выпускать
   нечего». Пустые changeset'ы уйдут со следующим настоящим выпуском.
4. `npm ci`, затем `npm run changeset:version`. Команда сама поднимает версии,
   пишет `CHANGELOG.md`, удаляет changeset'ы и обновляет `package-lock.json`.
   Ни версии, ни `CHANGELOG.md` руками не правишь — даже если текст
   changeset'а кривой: это правка к PR задачи, а не к выпуску, её называешь
   в отчёте.
5. Проверь дифф: версия поднялась у всех пакетов группы `fixed` и только у
   них, стенд и корневой `package.json` не тронуты, в `.changeset/` остались
   только `config.json` и `README.md`. Прогон: `npm run test:setup` (сторож
   версий) и `npx prettier --check .`.
6. Ветку переименуй по версии: `git branch -m release/v<версия>`.
7. Коммит `chore(release): <версия>`, пуш, `gh pr create` с заголовком
   `Выпуск <версия>`. В теле — раздел новой версии из `CHANGELOG.md` любого
   пакета группы: у `fixed` он один на всех.
8. Сообщи версию, ссылку на PR, итоговую строку прогона и вошедшие пункты
   CHANGELOG. Тесты красные — PR не открываешь, пишешь, что упало.

Проверка CI `changeset` на ветках `release/*` не запускается: changeset'ы в
выпуске уже удалены, и она уронила бы его. Поэтому ветку `release/*` ни для
чего, кроме выпуска, не заводишь.
