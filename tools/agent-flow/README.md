# agent-flow

Связка ClickUp ↔ Claude Code: задача идёт по статусам, на каждом её подхватывает
своя роль.

## Поток

```
ANALYSIS    → analyst   → комментарий #ANALYSIS → OVERVIEW (на владельца)
PLANNING    → techlead  → комментарий #PLANNING → OVERVIEW (на владельца)
IN PROGRESS → developer → ветка, тесты, PR, #DEV → OVERVIEW (на владельца)
APPROVED    → скрипт merge-approved.mjs → мерж PR → CLOSED
```

`OVERVIEW` — единственный способ вернуть задачу владельцу. На каком этапе она
вернулась, видно по хештегу последнего комментария.

## Размер задачи

Владелец вешает на задачу тег `simple`, `normal` или `hard`. Тега нет — задача
считается `normal`. Сервер отдаёт роли готовое поле `size`, разбирать теги ей
не нужно.

От размера зависит, сколько роль читает и сколько пишет:

| `size` | Читает | Пишет комментарий |
|---|---|---|
| `simple` | до 5 файлов | 800–1000 символов |
| `normal` | до 12 файлов | до 2000–2500 |
| `hard` | сколько нужно | до 3000–4000 |

**Тег можно менять между этапами** — в этом весь смысл: анализ бывает `hard`,
а планирование по готовой карте — уже `simple`. Роль смотрит на то, что стоит
в момент запуска.

Размер не влияет на обязательные шаги: программист пишет тесты и открывает PR
на любом размере.

## Модели ролей

Задаются в frontmatter каждой роли:

| Роль | Модель | Почему |
|---|---|---|
| аналитик | `opus` | нужен reasoning: понять задачу, увидеть риски |
| тимлид | `opus` | проектирование, выбор подхода |
| программист | `sonnet` | исполнение готового плана — выносливость, а не архитектура |

Программист — самая дорогая роль по токенам (у него больше всего вызовов
инструментов), и при этом самая механическая: план ему уже написали, границы
очертили. Поэтому именно он переведён на модель дешевле.

Если заметишь, что программист врёт в отчётах или нарушает границы слоёв —
верни ему `opus` и перемерь.

## Хештеги в ленте

| Хештег | Кто | Как ставится |
|---|---|---|
| `#ANALYSIS` | аналитик | сервером, по параметру `role` |
| `#PLANNING` | тимлид | сервером |
| `#DEV` | программист | сервером |
| `#overview` | владелец | руками |
| `#MERGE` | скрипт мержа | скриптом |

Комментарий владельца — последнее слово: он важнее и постановки, и плана. Роли
это знают. Если владелец забыл хештег, они всё равно опознают его комментарий:
всё, что не начинается с `#ANALYSIS`/`#PLANNING`/`#DEV`, написано владельцем.

## Побочные находки

Тимлид и программист могут завести новую задачу — `clickup_create_task`.
Это для проблем, которые всплывают по ходу работы, но в текущую задачу не
входят: иначе они оседают в комментарии и пропадают вместе с закрытой задачей.

Новая задача создаётся в том же списке, что и исходная, попадает сразу в
`OVERVIEW` и назначается на владельца — **в очередь ролей она сама не уходит**.
В описание дописывается ссылка на задачу-источник и этап, на котором находку
сделали. Размер роль может предложить тегом, но последнее слово за владельцем.

Аналитику инструмент не выдан: его работа и так заканчивается постановкой.

Роли **не переводят задачу друг другу напрямую**. Каждый переход через
`OVERVIEW` делает владелец вручную — это точка контроля, а не формальность.

## Настройка

1. Токен ClickUp (Settings → Apps → API Token) — в `.claude/settings.local.json`,
   который лежит в gitignore:

   ```json
   { "env": { "CLICKUP_TOKEN": "pk_..." } }
   ```

   MCP-сервер наследует окружение Claude Code, поэтому в `.mcp.json` токен
   упоминать не нужно. Подстановка `${CLICKUP_TOKEN}` там **не работает**:
   серверу уходит literal-строка, и ClickUp отвечает 401.

   Для запуска `merge-approved.mjs` из обычного терминала нужен ещё и
   `setx CLICKUP_TOKEN "pk_..."` — `settings.local.json` виден только
   Claude Code.

2. Создать статусы в ClickUp **руками через UI** — публичного API для этого нет.
   Набор: `ANALYSIS`, `PLANNING`, `IN PROGRESS`, `OVERVIEW`, `APPROVED`,
   `CLOSED`. Статусы задаются на уровне Space и наследуются всеми списками
   внутри, поэтому для проекта нужен отдельный Space — иначе набор протечёт в
   соседние проекты.

3. Заполнить `config.json`. `teamId` и `ownerId` уже проставлены. Дальше одно
   из двух:
   - `spaceId` — предпочтительно: задачи ищутся по всему Space, новые списки
     внутри проекта подхватываются без правки конфига;
   - `listId` — запасной вариант, работает по одному списку. Используется,
     только если `spaceId` пуст.

   `statuses` должны совпадать с ClickUp побуквенно.

4. Перезапустить Claude Code, проверить `/mcp` — сервер `clickup` должен быть
   в списке.

## Запуск ролей

Пока вручную, по одной задаче за раз:

```
/analyze <task_id>
/plan    <task_id>
/dev     <task_id>
```

Автоматический диспетчер (поллинг статусов) сознательно не сделан: сначала
нужно обкатать промпты ролей, иначе отлаживать придётся одновременно и роли,
и оркестрацию.

## Мерж

```powershell
node tools/agent-flow/merge-approved.mjs         # dry-run, ничего не меняет
node tools/agent-flow/merge-approved.mjs --yes   # мержит и закрывает задачи
```

LLM здесь не участвует — токены не тратятся. PR ищется по ID задачи в имени
ветки, поэтому ветка обязана называться `task/<task_id>-...`.
